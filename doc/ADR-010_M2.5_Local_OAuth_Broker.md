# ADR-010：M2.5 本机 OAuth Broker 与多 Agent Worker 授权拓扑

> **取代通知（2026-11-20）：本 ADR 已被 ADR-013 取代，不实施本机 OAuth Broker。** 本文的 HTTPS、CA、OAuth、CIMD / DCR、Grant、Refresh Token、Resource Audience 和 Broker / Worker 双服务设计均为历史提案，已从 M2.5 首版取消。保留本文仅用于审计此前的设计过程。


- 状态：**提议采用；HTTPS / OAuth 客户端兼容原型通过前不冻结**
- 日期：2026-11-20
- 决策范围：本机 OAuth Authorization Server、Gateway Resource Server、Agent 身份绑定
- 关联：ADR-007、ADR-008、ADR-009、M2.3 Agent Security、M2.4 Credential Provider

## 1. 问题

M2.5 使用 Streamable HTTP 后，必须认证连接到本机 Gateway 的 MCP Host。与此同时，Gateway Worker 还需要使用 M2.4 Agent Service Token 访问 AirBridge HTTP API。

这两条信任路径不能共用一个 Token，也不能让 MCP Host 配置持有内部 Agent Service Token。

## 2. 提议拓扑

建议采用一个由 AirBridge GUI / Gateway Supervisor 管理的本机 OAuth Broker，以及每 Agent 一个独立 MCP Resource Server Worker：

```text
Antigravity MCP Client ─┐
                       ├─ OAuth Access Token ──> Agent Worker (MCP Resource Server)
OpenCode MCP Client ───┘                               │
          │                                            │ Agent Service Token
          └──── OAuth Authorization Code + PKCE ───────┤
                                                       ▼
AirBridge GUI / Gateway Supervisor              AirBridge HTTP API
  └─ Local OAuth Broker (HTTPS)                  (Agent Security)
       ├─ Authorization Endpoint                      │
       ├─ Token Endpoint                               ▼
       ├─ Metadata / DCR / CIMD                   AirBridge Runtime
       └─ Consent / Grant Registry
```

此图为目标拓扑提议，不代表当前代码已实现。

### 网络边界（已确认的非目标）

该拓扑仅服务同一台 Windows 主机上的 MCP Client。Broker 与 Worker 通过 loopback 提供本机 HTTPS；不提供跨机器 / LAN / 公网 HTTPS MCP 服务，不把 HTTPS 服务通过 AirBridge ABFP 或串口转发。Host A 与 Host B 的通信继续完全使用既有 AirBridge 链路。若两台机器分别部署本机 Gateway，各自只服务本机 MCP Client，CA 私钥、服务器证书和用户信任均不在两台机器之间传输或共享。

### 2.1 固定默认地址与端口

**用户已确认的默认 TCP 端口：**
- Local OAuth Broker：38861，稳定 issuer 为 `https://localhost:38861/`。
- 首个 Antigravity MCP Resource Server：38862，endpoint 为 `https://localhost:38862/mcp`。
- 首个 OpenCode MCP Resource Server：38863，endpoint 为 `https://localhost:38863/mcp`。

Broker 对两个 Agent Worker 提供共同的 OAuth Authorization Server；每个 Worker 仍有独立 Resource Audience。Broker 和 Worker 只监听 loopback，且必须使用互不重复的端口。新增 Agent 实例有独立 Worker 端口并持久化；端口修改后的 issuer / Resource 迁移规则见 ADR-007。

## 3. 组件职责

### 3.1 Local OAuth Broker

由 GUI / Supervisor 拥有和管理，负责：
- MCP OAuth Authorization Server Metadata；
- Protected Resource Metadata 所引用的 Authorization Server 地址；
- Authorization Code + PKCE S256；
- DCR / CIMD 客户端注册和校验；
- 用户授权 / Consent；
- Token 签发、刷新、轮换、撤销；
- OAuth client、Agent ID、Resource Audience、Scope、授权状态的绑定；
- HTTPS 证书检查与服务健康状态；
- 监听固定 issuer / TCP 端口 38861（默认），并将稳定 issuer / metadata 地址发布给 Resource Server。

OAuth Broker 不直接调用 Capture / Allegro，也不负责 EDA 业务。

### 3.2 Agent Gateway Worker

每个 Worker 固定一个 AirBridge Agent ID，例如 `antigravity` / `opencode`。Worker 作为 MCP Resource Server：
- 接收 Streamable HTTP 请求；
- 对每个请求验证 Access Token；
- 验证 Token resource / audience 精确等于自身 MCP endpoint；
- 验证 Token 绑定的 Agent ID 等于自身固定 Agent ID；
- 验证所需 Scope；
- 将请求映射到对应 Agent 的 AirBridge HTTP API 凭据；
- 通过 M2.4 Credential Provider 读取该 Agent Service Token；
- 不读取、缓存或转发 MCP Client Access Token 作为下游 AirBridge API Token。

MCP Python SDK 的 Resource Server TokenVerifier 可作为 Worker Token 验证的集成点；Authorization Broker 仍需单独实现或集成。

### 3.3 GUI Supervisor

GUI Supervisor：
- 管理 OAuth Broker HTTPS 服务；
- 启停和监控各 Agent Worker；
- 提供 Agent 授权/撤销入口；
- 显示证书、OAuth、Worker、Credential Provider 的独立健康状态；
- 确保 GUI 正常退出时先停止 Worker，再关闭 OAuth Broker。

## 4. 授权绑定模型

一次 MCP Client 授权必须绑定以下数据：

| 字段 | 作用 |
|---|---|
| oauth_client_id | Antigravity / OpenCode 客户端的 OAuth client identity |
| agent_id | AirBridge 固定 Agent 身份 |
| resource | 具体 MCP Worker endpoint / audience |
| scopes | 用户授权的能力范围 |
| grant_id | 本次用户授权记录 |
| issued_at / expires_at | Token 生命周期 |
| revoked_at | 撤销状态 |

关键规则：
- OAuth client_id 不是 Agent ID，不能直接把两者视为相等；
- 同一个 client_id 不能自动访问所有 Agent Worker；
- 一个 Access Token 必须绑定一个明确的 Resource endpoint；
- Worker 在处理工具调用前验证 Agent ID、Resource 和 Scope；
- DCR / CIMD 只建立客户端注册身份，不代表获得 Agent 权限；
- 对未知客户端的授权必须显示客户端信息并要求用户确认；
- 凭据撤销应立即阻止后续授权/刷新；已有短期 Access Token 是否需要实时 Introspection 或短 TTL + 撤销缓存，需在实施中明确。

## 5. Token 存储与校验实现候选

### 5.1 Opaque Token + 本地授权数据库

Authorization Broker 生成高熵随机 Token，数据库只保存 Token 摘要。Worker 可通过受保护的本机数据访问接口或本地授权验证服务确认 Token 有效性。

优点：
- 可立即撤销；
- 服务端不需要把签名私钥发给 Worker；
- 数据库只保存 Token 摘要。

需要评估：
- 多 Worker 高频验证时的 SQLite 读取并发；
- 过期清理与 Refresh Token rotation；
- GUI 退出时数据库关闭顺序；
- Worker 读取数据库的最小 ACL。

### 5.2 签名 JWT + 撤销状态

Authorization Broker 使用受保护的签名私钥签发短期 JWT，Worker 使用公钥本地验证。

优点：
- 每次 MCP 请求可本地验证；
- 减少 Worker 对 Broker 的同步查询。

需要评估：
- 私钥存储与备份；
- Access Token 提前撤销延迟；
- 密钥轮换与 JWKS；
- Agent / resource / scope claim 的严格校验。

两种方案都必须实现 Resource Audience 精确绑定。不得把未校验的客户端 Token 原样传给 AirBridge HTTP API。

## 6. HTTPS 与证书管理 Gate

OAuth Broker 必须提供 HTTPS。目标是本机使用，不意味着可以忽略证书验证。

**用户已确认的部署阶段证书信任策略：**
- CA / localhost Server Certificate 的创建和 CA 公钥信任导入属于每台 M2.5 AirBridge 的部署阶段；不等到 Gateway ON 或第一次 MCP 连接时才执行。
- 每台部署主机在部署阶段获取适用于本机 localhost 的 CA 公钥信任材料；不设固定 Host A / B 为 CA 来源，也不手工从某台主机导出。正式 CA 签发 / 供应模型由 G-01 技术验证确定；不得把 CA 私钥放入普通安装包或经 AirBridge Runtime 跨机传输。
- 部署流程在目标 Windows 用户上下文展示证书用途、Subject、Thumbprint、有效期和 CurrentUser 范围；取得明确 Consent 后才将 CA 公钥导入该用户 `Cert:\CurrentUser\Root`。
- 不要求管理员权限，不写 LocalMachine 证书库。若安装程序需提升权限，CurrentUser Root 导入必须由目标用户上下文执行。
- CA 部署不代表 Gateway 启用。新安装仍默认 `gateway.enabled=false`，不启动 Broker 或 Worker。
- 用户拒绝 Consent 时 AirBridge 安装和 Core / Runtime 仍可用，但 Managed HTTPS / OAuth Gateway 不可用；后续只能经显式部署 Repair 再次征求 Consent，不能在普通 Gateway ON 操作中静默导入。
- 升级保留有效本机 CA、私钥关联、服务器证书和 CurrentUser 信任；缺失 / 过期 / 轮换必须在部署或 Repair 阶段明示并重新征求 Consent。
- 不得关闭 TLS 校验、忽略证书错误或降级为无认证 HTTP；拒绝信任不影响现有 stdio 和 AirBridge Core / Runtime。

**仍待技术验证：**
- 固定 HTTPS issuer / port，保证 OAuth metadata issuer URL 在重启后稳定；
- 证书 SAN 覆盖使用的 loopback host；
- 证书私钥存储在 Windows 当前用户受保护存储；
- CurrentUser 证书信任是否被 Antigravity / OpenCode 和默认浏览器各自的 TLS 栈正确识别；
- 更新、轮换、撤销、重装和卸载有明确流程；
- 不能关闭 TLS 校验、忽略证书错误或使用不安全的客户端 flag。

**Go / No-Go 必须以真实目标客户端完成 OAuth 流程为准，不能只以 PowerShell / curl 能访问 HTTPS 为准。若客户端不接受 CurrentUser 信任，不能扩大到 LocalMachine Root 或要求管理员权限来绕过；当前 Managed HTTPS Mode 应判定 No-Go 并重新评审。**

## 7. 生命周期与故障

- Gateway 总开关 OFF：不启动 Agent Worker；OAuth Broker 也不应作为独立公开服务常驻。
- Gateway ON：Supervisor 启动 OAuth Broker，再启动已启用 Agent Worker。
- Worker 停止：先排空并关闭 Worker；不必撤销用户授权。
- Agent 停用 / 撤销：Worker 停止，OAuth Broker 撤销该 Agent 对应授权；内部 M2.4 Service Token 是否撤销由用户在 Agent 管理流程确认。
- GUI 正常退出：依次停止 Worker，再关闭 OAuth Broker。
- GUI 崩溃：Worker 发现 Supervisor 进程退出后有界收敛；不能长期留下可调用 Gateway。
- OAuth Broker HTTPS 不健康：不能将 MCP Worker 标记为授权就绪；新授权与 Token refresh 应失败关闭。

### 7.1 升级安装与 Broker 持久化状态

升级安装必须保留 Broker 的授权连续性：
- 保留 OAuth Client Registration、有效 Grant、撤销记录、Token digest / 生命周期数据，以及验证和签发 Token 所需的持久化密钥材料。
- 保持 issuer、Authorization Server Metadata、Worker Resource Audience 和 endpoint 稳定；正常升级不应无故让用户重新授权。
- 按数据库 / 存储 schema 版本执行幂等迁移；修改前备份 Broker 持久化状态和密钥元数据，备份受当前 Windows 用户 ACL 保护；迁移失败必须回滚，不能清空 Grant Store 或重建全新的 issuer 身份。
- 不得将撤销状态回退为未撤销；过期 / 已撤销 Grant 不得因备份恢复或 schema 迁移重新有效。
- 保留 M2.4 Agent Service Credential 的既有 Credential Manager 条目；Broker 升级不能重签、轮换或撤销这些凭据。
- 保留仍有效的 AirBridge CurrentUser HTTPS 证书身份与私钥关联；不无故重新导入或改变信任范围。
- 客户端自己的 Access Token / Refresh Token Vault 由 Antigravity / OpenCode 管理；AirBridge 不读取、复制、备份、迁移、改写或删除。若某个 issuer / Resource 必须变化，只对受影响 Grant 明确提示重新授权。

若 Grant Store 损坏、schema 不支持、备份或回滚失败，Broker 不得启动为“空白新实例”；Managed HTTPS OAuth 保持不可用，GUI 显示恢复诊断，保留原始数据供恢复。

## 8. 安全边界

- 本机 loopback 只限制网络暴露面，不替代 OAuth；
- HTTPS 证书校验不可关闭；
- 所有 Token 均不得写入配置 JSON、日志、命令行、审计或诊断包；
- OAuth Access Token 与 M2.4 Agent Service Token 独立签发、独立存储、独立撤销；
- Worker 必须校验 audience / resource、Agent ID、Scope、expiry / revocation；
- Client 不得选择或声明服务端 Agent ID；
- 不得让一个 Worker 读取另一个 Agent 的凭据；
- 认证失败时请求不能进入 MCP Tool handler 或 AirBridge HTTP API。

## 9. 验收

- [ ] GUI 能启动 / 监控 / 停止 OAuth Broker HTTPS 服务。
- [ ] OAuth issuer URL 在正常重启和版本升级后稳定。
- [ ] 升级迁移保留 Client Registration、Grant / Revocation 状态、Token digest 和 issuer 所需密钥材料；不复活已撤销 Grant。
- [ ] Broker schema 迁移可重复、原子、可回滚；损坏 / 未知版本时不创建空白 Grant Store。
- [ ] 升级不改写 Antigravity / OpenCode 私有 Token Vault，不轮换或撤销 M2.4 Credential Manager 条目。
- [ ] Antigravity App / IDE / CLI 完成 OAuth 授权。
- [ ] OpenCode Desktop 完成 OAuth 授权。
- [ ] 每个 MCP Worker 的 Access Token 绑定正确 audience / Agent ID / Scope。
- [ ] Antigravity Token 不能调用 OpenCode Worker，反之亦然。
- [ ] Antigravity / OpenCode 两个精确 CIMD Metadata URL 被接受；其他 URL、相似域名、query / fragment、非标准端口和跨域重定向均拒绝。
- [ ] Antigravity IDE 2.6.0+ 按官方流程使用 CIMD；低版本 / 不支持 CIMD 时通过 DCR fallback。
- [ ] OpenCode 在 AS 启用 CIMD、公有客户端且没有自定义 redirect_uri 时使用 CIMD；不满足条件时按官方行为回退 DCR。
- [ ] DCR 注册只允许受支持的公共授权码客户端和 PKCE S256，redirect URI、grant / response types、token endpoint auth method 校验通过。
- [ ] DCR 元数据中的客户端名称、网站、图标和产品类型显示为未经验证的自述，不能冒充已验证官方客户端。
- [ ] 仅有 DCR / CIMD 注册、没有用户授权时不能访问 MCP tools，也不能自动获得 Scope。
- [ ] 同一 Client ID 对第二个 Agent / Resource 需要单独 Consent；Grant 精确绑定 Client ID / Agent ID / Resource Audience / Scope。
- [ ] DCR 限流、最大注册数、元数据尺寸限制、重复注册处理与审计测试通过。
- [ ] 撤销后不能再刷新 Token；已发行 Access Token 的失效策略符合预期。
- [ ] MCP Client OAuth Token 不会被透传到 AirBridge HTTP API。
- [ ] M2.4 Service Token 仍从 Credential Provider 读取，不进入 MCP Client。
- [ ] GUI / Broker 异常退出后 Worker 有界退出。
- [ ] 证书无效、过期、被撤销或不受信任时拒绝连接，不跳过验证。

## 11. v0.2：Bearer Token TLS、撤销与本机证书管理补充

### 11.1 OAuth Resource Server 也必须走 HTTPS

本地 MCP Worker 是 OAuth Protected Resource Server。MCP Authorization 规范要求 Authorization Server endpoints 使用 HTTPS；RFC 6750 对 Bearer Token Usage 要求客户端到 Resource Server 的 Token 请求同样使用 TLS。因此不能只给 OAuth Broker 配置 HTTPS，而仍让 MCP Worker 使用明文 HTTP。

M2.5 托管模式必须满足：
- Broker 的 issuer、authorization、token、metadata endpoint 均使用 HTTPS；
- 每个 Agent Worker 的 MCP Resource Server endpoint 使用 HTTPS；
- MCP Client 必须验证证书链；
- 仅 OAuth Authorization Code redirect URI 在规范允许时使用 loopback HTTP；
- 不允许通过环境变量或启动选项关闭 TLS 验证。

### 11.2 初版建议采用 Opaque Access Token + Broker Introspection

初版推荐使用 Opaque Token，而不是先引入分布式 JWT 私钥：
- Broker 为 Access Token / Refresh Token 生成密码学安全随机值；
- 授权数据库只保存 Token 的 SHA-256 摘要，不保存明文；
- Worker 收到 MCP 请求后，通过受当前 Windows 用户 ACL 保护的本机 IPC（建议 Named Pipe）向 Broker 查询 Token；
- Broker 校验 Token digest、expiry、revocation、client_id、Agent ID、Resource Audience 和 Scope；
- 返回最小非秘密授权声明；
- Worker 仅在授权结果完整、Audience 与自身 endpoint 完全一致、Agent ID 与进程固定 Agent ID 相符且 Scope 足够时进入 MCP Tool handler；
- Broker / IPC / Grant Store 不可用时 Worker 必须 fail closed，返回 503 或适当授权错误，不能放行。

选择 Opaque Token 的原因：本机使用频率相对可控，便于撤销后立即拒绝后续请求；Worker 不需要持有签名私钥。需要在 Windows 原型中验证 Named Pipe 请求并发、Worker 重连、Broker shutdown 和 SQLite WAL 查询性能。

### 11.3 Token 生命周期与撤销

- Access Token 使用短有效期，M2.5 PoC 建议不超过 1 小时，最终时间由客户端兼容测试决定；
- Public Client 的 Refresh Token 必须轮换；旧 Refresh Token 被再次使用时应撤销相关 Token Family / Grant 并记录安全事件；
- GUI 撤销 Grant 时，Broker 原子标记该 Grant 和其 Refresh Token 已撤销；Worker 对之后的每次请求做即时校验，所以旧 Access Token 后续立即不能使用；
- 已通过校验并进入 Tool handler 的在途请求不因撤销操作自动中断；撤销的安全语义是阻止后续请求；
- 用户在 Antigravity / OpenCode 中保留的旧 Token 可由客户端自己删除；即使客户端仍保留，Broker 也必须拒绝它；
- 日志与审计仅记录 grant_id、client_id、Agent ID、resource、scope、结果码和时间，绝不记录 Token 或 Authorization Header。

### 11.4 单一 OAuth Broker，多 Worker Resource Audience

一个本机 OAuth Broker 可服务多个独立 Agent Worker，但每个 MCP Worker 必须有独立 Resource Audience：
- Antigravity Worker 使用固定 audience / endpoint；
- OpenCode Worker 使用不同 audience / endpoint；
- 同一 Access Token 不得同时授权两个 Worker；
- OAuth metadata 的 Resource / Audience 必须与 Worker 实际公开 URL 精确一致；
- Worker 不允许从 Client 请求参数选择 Agent ID 或 Resource；
- Worker 实际调用 AirBridge HTTP API 时，仍通过 M2.4 Credential Provider 读取自身 Agent Service Token。

### 11.5 CIMD 白名单优先与 DCR 兼容回退（D-07，用户已确认）

本机 Broker 首批只识别以下精确官方 Client ID Metadata URL：
- Antigravity：`https://antigravity.google/oauth/client-metadata.json`；
- OpenCode：`https://opencode.ai/oauth/opencode/client.json`。

Broker Authorization Server Metadata 必须提供稳定且非空的 `issuer`、`code_challenge_methods_supported=["S256"]`，并在兼容时设置 `client_id_metadata_document_supported=true` 和 `token_endpoint_auth_methods_supported=["none"]`（明确支持 Public Client）；同时发布 DCR `registration_endpoint` 作为回退。Antigravity IDE 2.6.0+ 使用 CIMD；旧版本 / 未采用 CIMD 的受支持版本需要通过 DCR 完成兼容。OpenCode 在 AS 支持 CIMD、公有客户端且没有自定义 `redirect_uri` 时采用 CIMD；自定义 redirect URI 会使其回退 DCR。AirBridge 不在 MCP Host 配置中写入预注册 `client_id` / `client_secret` 或自定义 `redirect_uri`。

**CIMD URL 策略：**
- 只接受上列完整 URL 精确匹配；禁止任意 URL、用户自定义 Metadata URL、通配域名、URL query / fragment、非标准端口与跨域 redirect。
- 优先对这两个官方 Client ID 及其官方 metadata / redirect URI 规则预登记，不发起网络抓取。除非技术实现确有需要，不实现通用 CIMD URL fetch。
- 如实现为验证而读取 CIMD metadata，只允许精确白名单目标，禁止跨域重定向，并限制 TLS、DNS、响应体大小、超时、内容类型与缓存。任何重定向目标都不得超出原始官方 host。
- Antigravity CIMD redirect URI 固定为 `https://antigravity.google/oauth-callback`，不得扩大成任意 Antigravity 域名。
- OpenCode loopback callback 严格执行其 Client Metadata 文档和 RFC 8252 规则；只接受允许的 loopback host / scheme / path 组合，动态端口仅在该客户端规则明确允许时接受。授权码兑换时 redirect URI 必须与授权请求一致。
- 不基于 Client Metadata 中的名称、logo 或网站声明授予信任或权限。

**DCR fallback 与 Consent：**
- DCR 仅是 Antigravity / OpenCode 首批支持版本的兼容回退，不意味着 Generic / Manual MCP Client 在首版获得支持。
- 仅接受首批客户端所需的公共 Authorization Code 客户端 profile，强制 PKCE S256；拒绝不支持的 grant type、response type 和 token endpoint auth method。
- Antigravity redirect URI 严格限制为 `https://antigravity.google/oauth-callback`。
- OpenCode loopback redirect URI 严格限制为官方 metadata 列出的 `http://127.0.0.1/callback`、`http://localhost/callback`，及旧客户端 `http://127.0.0.1/mcp/oauth/callback`；按 RFC 8252 允许动态 loopback port，不接受其它 host / scheme / path。授权请求和 token request 中 redirect_uri 必须一致。
- 限制注册速率 / 数量 / metadata 大小并记录审计事件。
- DCR 返回的客户端名称、URL、Logo、产品类型等都视为未经验证的声明。GUI 必须标注“未验证的 OAuth Client”，让用户检查后再 Consent；不能显示“已验证的 Antigravity / OpenCode”。
- CIMD / DCR 注册只创建 OAuth Client Registration，不签发 Grant、不自动授予 Agent / Scope，也不能访问任何 MCP Tool。
- 用户对每个 Grant 单独 Consent，并绑定 `oauth_client_id + agent_instance_id + resource/audience + scopes`。同一个 Client ID 对另一个 Agent / Resource 的首次访问需要新的 Consent；CIMD allowlist 绝不代表自动授权。
- Authorization request 与 Token endpoint 继续验证 PKCE S256、OAuth state、redirect URI、issuer 和 RFC 8707 resource / audience。授权 / 撤销状态由 Broker 独立维护。

### 11.6 Windows 本机证书信任模型

PoC 建议研究当前 Windows 用户级证书模型：
- 用户专属本地 CA 私钥存放在 `Cert:\CurrentUser\My` 或等价受保护密钥容器；
- CA 公证书可在用户明确确认后导入 `Cert:\CurrentUser\Root`；
- OAuth Broker 和 MCP Worker 使用的 server certificate SAN 覆盖 `localhost`，如使用 IP URL 还必须包含对应 IP SAN；
- 证书私钥不可放在普通 JSON、仓库、明文配置或诊断包中；
- 固定 issuer hostname / port，证书续期支持新旧证书短期重叠；
- GUI 记录本产品创建的证书 thumbprint、store、有效期和关联服务；
- 卸载/重置只删除本产品管理且确认不再使用的证书，不触碰其他 Root / Personal entries；
- 不默认修改 LocalMachine Root，不要求不必要的管理员权限；
- 用户拒绝证书安装、证书失效或不受目标客户端信任时，HTTPS OAuth Managed Mode 保持不可用，不回退到 HTTP。

Microsoft 的 `New-SelfSignedCertificate` 提供 localhost SAN 示例，可用于初始验证；Microsoft 文档将其定位为测试用途，不能仅凭 PowerShell / curl 测试就判定目标 MCP 客户端信任兼容。真实 Antigravity / OpenCode HTTP 栈的证书信任是 Go / No-Go 项。

### 11.7 授权状态来源

AirBridge GUI 不读取客户端 OAuth Token Vault：
- Broker Grant Registry 是“本机已签发授权”的权威状态；
- Worker 最近一次成功验证的请求是“客户端最近已完成认证”的证据；
- MCP initialize / tools/list 是协议功能可用的证据；
- 客户端配置文件仅能证明 endpoint 配置存在。

四种信息必须分别展示，不能把 Grant Registry 中的记录当成客户端当前持有有效 Token 的证明。

### 11.8 新增验收

- [ ] OAuth Broker 与两个 MCP Worker 的 URL 均为 HTTPS。
- [ ] 客户端验证 TLS 证书链；无效证书时拒绝连接。
- [ ] Token 只在 TLS 连接中通过 Authorization Header 传输。
- [ ] Opaque Token 明文从不落入数据库、日志或诊断包。
- [ ] Worker 每次请求均验证 Token expiry / revocation / audience / Agent / scope。
- [ ] Grant 撤销后，旧 Access Token 的下一次请求被拒绝。
- [ ] Refresh Token rotation 与旧 Token 重放检测通过。
- [ ] OAuth Broker IPC 不可用时 Worker fail closed。
- [ ] DCR / CIMD 无用户授权时不能访问 Agent Worker。
- [ ] CIMD URL SSRF、重定向、DNS rebinding 与私网地址攻击测试通过。
- [ ] 证书安装 / 轮换 / 重启 / 卸载后 Antigravity 和 OpenCode 仍可正常验证 TLS。

### 11.7 本机 CA 的主机归属与 CurrentUser 信任边界

M2.5 Broker / Worker endpoint 仅监听 loopback，客户端 URL 使用 `localhost`。因此 `localhost` 总是解析到 MCP Client 所在机器；Client 与对应 Gateway 必须运行在同一台 Windows 主机。不能把 Host A / Host B 设为固定 CA 签发端，也不能让一端通过 `localhost` 访问另一端的 Gateway。

AirBridge 在两台主机间的 Runtime / 串口链路只承载既有通用远程通信，不会把本机 HTTPS endpoint 或 CurrentUser 信任库转发到对端。

本机证书管理采用 per-machine / per-Windows-user 模型：
- 每台部署 M2.5 AirBridge 的机器都在部署阶段获取适用于本机 localhost 的 CA 公钥信任材料并完成 CurrentUser 导入；Root Thumbprint 是否相同由最终 CA 供应模型决定。
- CA 私钥不得放入普通安装包、导出到共享目录、写入仓库或通过 AirBridge Runtime 跨机传输。升级保留有效证书和所需私钥关联，不无故重建或替换。
- CA 公钥在每台部署 M2.5 的机器的目标 Windows 用户 CurrentUser Root 中，于部署阶段经明确同意后建立信任。该存储不是跨机器共享的用户配置。
- 同一机器不同 Windows 用户的 CurrentUser 信任彼此独立。默认 PoC 使用同一 Windows 用户运行 AirBridge GUI / Gateway 和 MCP Client；跨用户部署需单独验证客户端用户的 CA 信任与 Gateway 用户的私钥 ACL。
- A / B 若都部署 M2.5 AirBridge，应分别在各自部署流程中完成 CA 公钥导入和用户 Consent；即使 Gateway OFF 也完成 CA 信任准备，但不启动 Broker / Worker。

该规则是 loopback + CurrentUser 产品约束的技术落地方式，不增加对端 CA 信任、LAN 监听或集中式跨机器 CA 的能力。
