# ADR-010：M2.5 本机 OAuth Broker 与多 Agent Worker 授权拓扑

- 状态：**提议采用；HTTPS / OAuth 客户端兼容原型通过前不冻结**
- 日期：2026-11-20
- 决策范围：本机 OAuth Authorization Server、Gateway Resource Server、Agent 身份绑定
- 关联：ADR-007、ADR-008、ADR-009、M2.3 Agent Security、M2.4 Credential Provider

## 1. 问题

M2.5 使用 Streamable HTTP 后，必须认证连接到本机 Gateway 的 MCP Host。与此同时，Gateway Worker 还需要使用 M2.4 Agent Service Token 访问 AirBridge HTTP API。

这两条信任路径不能共用一个 Token，也不能让 MCP Host 配置持有内部 Agent Service Token。

## 2. 提议拓扑

建议采用一个由 AirBridge GUI / Gateway Supervisor 管理的本机 OAuth Broker，以及每 Agent 一个独立 MCP Resource Server Worker：

```text
Antigravity MCP Client ─┐
                       ├─ OAuth Access Token ──> Agent Worker (MCP Resource Server)
OpenCode MCP Client ───┘                               │
          │                                            │ Agent Service Token
          └──── OAuth Authorization Code + PKCE ───────┤
                                                       ▼
AirBridge GUI / Gateway Supervisor              AirBridge HTTP API
  └─ Local OAuth Broker (HTTPS)                  (Agent Security)
       ├─ Authorization Endpoint                      │
       ├─ Token Endpoint                               ▼
       ├─ Metadata / DCR / CIMD                   AirBridge Runtime
       └─ Consent / Grant Registry
```

此图为目标拓扑提议，不代表当前代码已实现。

## 3. 组件职责

### 3.1 Local OAuth Broker

由 GUI / Supervisor 拥有和管理，负责：
- MCP OAuth Authorization Server Metadata；
- Protected Resource Metadata 所引用的 Authorization Server 地址；
- Authorization Code + PKCE S256；
- DCR / CIMD 客户端注册和校验；
- 用户授权 / Consent；
- Token 签发、刷新、轮换、撤销；
- OAuth client、Agent ID、Resource Audience、Scope、授权状态的绑定；
- HTTPS 证书检查与服务健康状态。

OAuth Broker 不直接调用 Capture / Allegro，也不负责 EDA 业务。

### 3.2 Agent Gateway Worker

每个 Worker 固定一个 AirBridge Agent ID，例如 `antigravity` / `opencode`。Worker 作为 MCP Resource Server：
- 接收 Streamable HTTP 请求；
- 对每个请求验证 Access Token；
- 验证 Token resource / audience 精确等于自身 MCP endpoint；
- 验证 Token 绑定的 Agent ID 等于自身固定 Agent ID；
- 验证所需 Scope；
- 将请求映射到对应 Agent 的 AirBridge HTTP API 凭据；
- 通过 M2.4 Credential Provider 读取该 Agent Service Token；
- 不读取、缓存或转发 MCP Client Access Token 作为下游 AirBridge API Token。

MCP Python SDK 的 Resource Server TokenVerifier 可作为 Worker Token 验证的集成点；Authorization Broker 仍需单独实现或集成。

### 3.3 GUI Supervisor

GUI Supervisor：
- 管理 OAuth Broker HTTPS 服务；
- 启停和监控各 Agent Worker；
- 提供 Agent 授权/撤销入口；
- 显示证书、OAuth、Worker、Credential Provider 的独立健康状态；
- 确保 GUI 正常退出时先停止 Worker，再关闭 OAuth Broker。

## 4. 授权绑定模型

一次 MCP Client 授权必须绑定以下数据：

| 字段 | 作用 |
|---|---|
| oauth_client_id | Antigravity / OpenCode 客户端的 OAuth client identity |
| agent_id | AirBridge 固定 Agent 身份 |
| resource | 具体 MCP Worker endpoint / audience |
| scopes | 用户授权的能力范围 |
| grant_id | 本次用户授权记录 |
| issued_at / expires_at | Token 生命周期 |
| revoked_at | 撤销状态 |

关键规则：
- OAuth client_id 不是 Agent ID，不能直接把两者视为相等；
- 同一个 client_id 不能自动访问所有 Agent Worker；
- 一个 Access Token 必须绑定一个明确的 Resource endpoint；
- Worker 在处理工具调用前验证 Agent ID、Resource 和 Scope；
- DCR / CIMD 只建立客户端注册身份，不代表获得 Agent 权限；
- 对未知客户端的授权必须显示客户端信息并要求用户确认；
- 凭据撤销应立即阻止后续授权/刷新；已有短期 Access Token 是否需要实时 Introspection 或短 TTL + 撤销缓存，需在实施中明确。

## 5. Token 存储与校验实现候选

### 5.1 Opaque Token + 本地授权数据库

Authorization Broker 生成高熵随机 Token，数据库只保存 Token 摘要。Worker 可通过受保护的本机数据访问接口或本地授权验证服务确认 Token 有效性。

优点：
- 可立即撤销；
- 服务端不需要把签名私钥发给 Worker；
- 数据库只保存 Token 摘要。

需要评估：
- 多 Worker 高频验证时的 SQLite 读取并发；
- 过期清理与 Refresh Token rotation；
- GUI 退出时数据库关闭顺序；
- Worker 读取数据库的最小 ACL。

### 5.2 签名 JWT + 撤销状态

Authorization Broker 使用受保护的签名私钥签发短期 JWT，Worker 使用公钥本地验证。

优点：
- 每次 MCP 请求可本地验证；
- 减少 Worker 对 Broker 的同步查询。

需要评估：
- 私钥存储与备份；
- Access Token 提前撤销延迟；
- 密钥轮换与 JWKS；
- Agent / resource / scope claim 的严格校验。

两种方案都必须实现 Resource Audience 精确绑定。不得把未校验的客户端 Token 原样传给 AirBridge HTTP API。

## 6. HTTPS 与证书管理 Gate

OAuth Broker 必须提供 HTTPS。目标是本机使用，不意味着可以忽略证书验证。

待验证设计：
- 固定 HTTPS issuer / port，保证 OAuth metadata issuer URL 在重启后稳定；
- 证书 SAN 覆盖使用的 loopback host；
- 证书私钥存储在 Windows 当前用户受保护存储；
- 安装和信任方式最小化，优先 CurrentUser 范围，避免未经必要的机器级 Root 修改；
- 更新、撤销、重装和卸载有明确流程；
- Antigravity / OpenCode / 默认浏览器都必须正确验证证书链；
- 不能关闭 TLS 校验、忽略证书错误或使用不安全的客户端 flag。

**Go / No-Go 必须以真实目标客户端完成 OAuth 流程为准，不能只以 PowerShell / curl 能访问 HTTPS 为准。**

## 7. 生命周期与故障

- Gateway 总开关 OFF：不启动 Agent Worker；OAuth Broker 也不应作为独立公开服务常驻。
- Gateway ON：Supervisor 启动 OAuth Broker，再启动已启用 Agent Worker。
- Worker 停止：先排空并关闭 Worker；不必撤销用户授权。
- Agent 停用 / 撤销：Worker 停止，OAuth Broker 撤销该 Agent 对应授权；内部 M2.4 Service Token 是否撤销由用户在 Agent 管理流程确认。
- GUI 正常退出：依次停止 Worker，再关闭 OAuth Broker。
- GUI 崩溃：Worker 发现 Supervisor 进程退出后有界收敛；不能长期留下可调用 Gateway。
- OAuth Broker HTTPS 不健康：不能将 MCP Worker 标记为授权就绪；新授权与 Token refresh 应失败关闭。

## 8. 安全边界

- 本机 loopback 只限制网络暴露面，不替代 OAuth；
- HTTPS 证书校验不可关闭；
- 所有 Token 均不得写入配置 JSON、日志、命令行、审计或诊断包；
- OAuth Access Token 与 M2.4 Agent Service Token 独立签发、独立存储、独立撤销；
- Worker 必须校验 audience / resource、Agent ID、Scope、expiry / revocation；
- Client 不得选择或声明服务端 Agent ID；
- 不得让一个 Worker 读取另一个 Agent 的凭据；
- 认证失败时请求不能进入 MCP Tool handler 或 AirBridge HTTP API。

## 9. 验收

- [ ] GUI 能启动 / 监控 / 停止 OAuth Broker HTTPS 服务。
- [ ] OAuth issuer URL 在正常重启后稳定。
- [ ] Antigravity App / IDE / CLI 完成 OAuth 授权。
- [ ] OpenCode Desktop 完成 OAuth 授权。
- [ ] 每个 MCP Worker 的 Access Token 绑定正确 audience / Agent ID / Scope。
- [ ] Antigravity Token 不能调用 OpenCode Worker，反之亦然。
- [ ] 仅有 DCR / CIMD 注册、没有用户授权时不能访问 MCP tools。
- [ ] 撤销后不能再刷新 Token；已发行 Access Token 的失效策略符合预期。
- [ ] MCP Client OAuth Token 不会被透传到 AirBridge HTTP API。
- [ ] M2.4 Service Token 仍从 Credential Provider 读取，不进入 MCP Client。
- [ ] GUI / Broker 异常退出后 Worker 有界退出。
- [ ] 证书无效、过期、被撤销或不受信任时拒绝连接，不跳过验证。

## 11. v0.2：Bearer Token TLS、撤销与本机证书管理补充

### 11.1 OAuth Resource Server 也必须走 HTTPS

本地 MCP Worker 是 OAuth Protected Resource Server。MCP Authorization 规范要求 Authorization Server endpoints 使用 HTTPS；RFC 6750 对 Bearer Token Usage 要求客户端到 Resource Server 的 Token 请求同样使用 TLS。因此不能只给 OAuth Broker 配置 HTTPS，而仍让 MCP Worker 使用明文 HTTP。

M2.5 托管模式必须满足：
- Broker 的 issuer、authorization、token、metadata endpoint 均使用 HTTPS；
- 每个 Agent Worker 的 MCP Resource Server endpoint 使用 HTTPS；
- MCP Client 必须验证证书链；
- 仅 OAuth Authorization Code redirect URI 在规范允许时使用 loopback HTTP；
- 不允许通过环境变量或启动选项关闭 TLS 验证。

### 11.2 初版建议采用 Opaque Access Token + Broker Introspection

初版推荐使用 Opaque Token，而不是先引入分布式 JWT 私钥：
- Broker 为 Access Token / Refresh Token 生成密码学安全随机值；
- 授权数据库只保存 Token 的 SHA-256 摘要，不保存明文；
- Worker 收到 MCP 请求后，通过受当前 Windows 用户 ACL 保护的本机 IPC（建议 Named Pipe）向 Broker 查询 Token；
- Broker 校验 Token digest、expiry、revocation、client_id、Agent ID、Resource Audience 和 Scope；
- 返回最小非秘密授权声明；
- Worker 仅在授权结果完整、Audience 与自身 endpoint 完全一致、Agent ID 与进程固定 Agent ID 相符且 Scope 足够时进入 MCP Tool handler；
- Broker / IPC / Grant Store 不可用时 Worker 必须 fail closed，返回 503 或适当授权错误，不能放行。

选择 Opaque Token 的原因：本机使用频率相对可控，便于撤销后立即拒绝后续请求；Worker 不需要持有签名私钥。需要在 Windows 原型中验证 Named Pipe 请求并发、Worker 重连、Broker shutdown 和 SQLite WAL 查询性能。

### 11.3 Token 生命周期与撤销

- Access Token 使用短有效期，M2.5 PoC 建议不超过 1 小时，最终时间由客户端兼容测试决定；
- Public Client 的 Refresh Token 必须轮换；旧 Refresh Token 被再次使用时应撤销相关 Token Family / Grant 并记录安全事件；
- GUI 撤销 Grant 时，Broker 原子标记该 Grant 和其 Refresh Token 已撤销；Worker 对之后的每次请求做即时校验，所以旧 Access Token 后续立即不能使用；
- 已通过校验并进入 Tool handler 的在途请求不因撤销操作自动中断；撤销的安全语义是阻止后续请求；
- 用户在 Antigravity / OpenCode 中保留的旧 Token 可由客户端自己删除；即使客户端仍保留，Broker 也必须拒绝它；
- 日志与审计仅记录 grant_id、client_id、Agent ID、resource、scope、结果码和时间，绝不记录 Token 或 Authorization Header。

### 11.4 单一 OAuth Broker，多 Worker Resource Audience

一个本机 OAuth Broker 可服务多个独立 Agent Worker，但每个 MCP Worker 必须有独立 Resource Audience：
- Antigravity Worker 使用固定 audience / endpoint；
- OpenCode Worker 使用不同 audience / endpoint；
- 同一 Access Token 不得同时授权两个 Worker；
- OAuth metadata 的 Resource / Audience 必须与 Worker 实际公开 URL 精确一致；
- Worker 不允许从 Client 请求参数选择 Agent ID 或 Resource；
- Worker 实际调用 AirBridge HTTP API 时，仍通过 M2.4 Credential Provider 读取自身 Agent Service Token。

### 11.5 CIMD / DCR 注册的 SSRF 控制

MCP Authorization 规范提醒，Authorization Server 获取任意 CIMD Metadata URL 可能产生 SSRF 风险。

首批 Antigravity / OpenCode 集成优先使用已知官方 Client Metadata URL 的 allowlist / pre-registration：
- Antigravity：`https://antigravity.google/oauth/client-metadata.json`；
- OpenCode：`https://opencode.ai/oauth/opencode/client.json`（以目标 OpenCode 版本官方文档为准）。

如启用通用 CIMD URL fetch，必须：
- 仅允许 HTTPS；
- 阻止 loopback、私网、link-local、云 metadata 和内部 DNS 域；
- 对 DNS 解析结果和每次重定向重新执行目标地址校验；
- 限制响应体大小、超时、内容类型和缓存；
- 防止 DNS rebinding；
- 不因 Client Metadata 声称的名称/图标而跳过用户 Consent。

DCR 注册成功不代表 Agent 已获准访问资源；Grant 仍必须由用户确认并绑定 Agent / Resource / Scope。

### 11.6 Windows 本机证书信任模型

PoC 建议研究当前 Windows 用户级证书模型：
- 用户专属本地 CA 私钥存放在 `Cert:\CurrentUser\My` 或等价受保护密钥容器；
- CA 公证书可在用户明确确认后导入 `Cert:\CurrentUser\Root`；
- OAuth Broker 和 MCP Worker 使用的 server certificate SAN 覆盖 `localhost`，如使用 IP URL 还必须包含对应 IP SAN；
- 证书私钥不可放在普通 JSON、仓库、明文配置或诊断包中；
- 固定 issuer hostname / port，证书续期支持新旧证书短期重叠；
- GUI 记录本产品创建的证书 thumbprint、store、有效期和关联服务；
- 卸载/重置只删除本产品管理且确认不再使用的证书，不触碰其他 Root / Personal entries；
- 不默认修改 LocalMachine Root，不要求不必要的管理员权限；
- 用户拒绝证书安装、证书失效或不受目标客户端信任时，HTTPS OAuth Managed Mode 保持不可用，不回退到 HTTP。

Microsoft 的 `New-SelfSignedCertificate` 提供 localhost SAN 示例，可用于初始验证；Microsoft 文档将其定位为测试用途，不能仅凭 PowerShell / curl 测试就判定目标 MCP 客户端信任兼容。真实 Antigravity / OpenCode HTTP 栈的证书信任是 Go / No-Go 项。

### 11.7 授权状态来源

AirBridge GUI 不读取客户端 OAuth Token Vault：
- Broker Grant Registry 是“本机已签发授权”的权威状态；
- Worker 最近一次成功验证的请求是“客户端最近已完成认证”的证据；
- MCP initialize / tools/list 是协议功能可用的证据；
- 客户端配置文件仅能证明 endpoint 配置存在。

四种信息必须分别展示，不能把 Grant Registry 中的记录当成客户端当前持有有效 Token 的证明。

### 11.8 新增验收

- [ ] OAuth Broker 与两个 MCP Worker 的 URL 均为 HTTPS。
- [ ] 客户端验证 TLS 证书链；无效证书时拒绝连接。
- [ ] Token 只在 TLS 连接中通过 Authorization Header 传输。
- [ ] Opaque Token 明文从不落入数据库、日志或诊断包。
- [ ] Worker 每次请求均验证 Token expiry / revocation / audience / Agent / scope。
- [ ] Grant 撤销后，旧 Access Token 的下一次请求被拒绝。
- [ ] Refresh Token rotation 与旧 Token 重放检测通过。
- [ ] OAuth Broker IPC 不可用时 Worker fail closed。
- [ ] DCR / CIMD 无用户授权时不能访问 Agent Worker。
- [ ] CIMD URL SSRF、重定向、DNS rebinding 与私网地址攻击测试通过。
- [ ] 证书安装 / 轮换 / 重启 / 卸载后 Antigravity 和 OpenCode 仍可正常验证 TLS。
