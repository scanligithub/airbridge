# ADR-012：M2.5 Agent 扩展与 MCP Client Adapter 注册机制

- 文档编号：AB-M2.5-ADR-012
- 版本：0.1
- 日期：2026-11-20
- 状态：**提案，待产品评审**
- 关联：ADR-007、ADR-008、ADR-009、ADR-010；M2.5 架构设计 v0.3；GUI 规范 v0.3
- 范围：AirBridge 如何从 Antigravity / OpenCode 扩展到其他 MCP Client / Agent Host

## 1. 背景与问题

M2.5 当前文档以 Antigravity、OpenCode 为首批目标 MCP Client。若把 Agent ID、Worker 启动参数、OAuth 注册策略、GUI 页面和配置代码直接写死为这两个产品，后续增加 Cursor、VS Code Copilot、Cline 或其他 MCP Client 时，就会不断修改 Gateway 核心逻辑，形成客户端与 Gateway 的强耦合。

这不是期望的长期架构。AirBridge Gateway 应是通用 MCP Server 接入层；客户端产品差异应封装在独立 Adapter 中。

另一个必须区分的问题是：**支持 MCP 远程协议，不等于 AirBridge 已经支持该客户端的自动配置。** 各 MCP Host 的配置文件路径、JSON schema、OAuth 启动入口、配置优先级和插件机制可能不同。客户端是否能连接属于协议兼容性，AirBridge 是否能自动发现和配置它属于 Adapter 兼容性。

## 2. 决策提案

采用三层扩展模型：

1. **MCP Client Type Registry（客户端类型注册表）**：描述一种 Agent Host 产品及其能力、版本范围和接入方式。
2. **MCP Client Configuration Adapter（客户端配置适配器）**：封装某种产品的发现、配置检查、当前用户配置写入、验证和移除操作。
3. **通用 MCP Client 手动接入（Generic / Manual）**：对于没有专用 Adapter、但通过 AirBridge 兼容性检查的 MCP Client，GUI 生成 endpoint、OAuth 说明和配置片段，由用户在客户端自己的设置界面中手动添加。

Gateway Worker、OAuth Broker、Agent Security 和 AirBridge Runtime 不因客户端品牌而分叉。新增产品原则上只需新增一个 Type Descriptor 和/或 Adapter。

## 3. 核心模型：客户端类型与 Agent 实例分离

不得把产品类型名称直接当作唯一 Agent 身份。

建议区分：

| 字段 | 含义 | 示例 |
|---|---|---|
| `client_type_id` | 客户端产品 / 类型的稳定 ID | `antigravity`、`opencode`、`cursor`、`vscode-copilot`、`cline` |
| `adapter_id` | 配置适配器 ID；可与 client_type_id 相同，也可使用 generic | `antigravity.config.v1`、`generic.manual.v1` |
| `agent_instance_id` | 本机注册实例的唯一稳定 ID | AirBridge 生成的唯一 ID |
| `display_name` | GUI 展示名称，可由用户编辑 | `Cursor - Work Profile` |
| `resource_audience` | 该 Agent Worker 的 OAuth Resource Audience | 该实例的 canonical HTTPS endpoint |
| `credential_ref` | 指向 M2.4 Credential Provider 的非秘密引用 | 内部凭据记录 ID |
| `scopes` | 该实例获准使用的权限集合 | 默认只读 Scope |

同一个 MCP Client 产品可以注册多个实例，例如不同用户配置、不同桌面配置或不同 Agent Profile。每个实例必须拥有独立的 `agent_instance_id`、Service Credential、OAuth Grant 绑定、Resource Audience、Scope 和 Worker 运行状态。

Worker 的内部启动参数应引用注册实例 ID，而不是把产品枚举写死在程序中。例如：

```powershell
AirBridge.exe --gateway-worker --agent-instance-id <stable-id>
```

该命令仅为内部设计示意，不是当前已实现接口。不得在命令行中传递 Token、密码或其他秘密。

## 4. 三种接入等级

### 4.1 Managed Adapter（专用自动配置适配器）

具有经过验证的专用 Adapter 的 MCP Client，可由 GUI 提供完整管理体验：
- 自动检测客户端是否安装及版本；
- 按该客户端官方 schema 定位当前用户级配置；
- 读取并保留现有配置；
- 只新增 / 更新 / 删除 AirBridge 自己管理的 MCP Server 条目；
- 备份、原子写入、重新读取和验证；
- 引导用户进入该客户端自己的 OAuth Authenticate 流程；
- 显示配置状态、授权观察状态、Worker 状态和最近成功请求。

**首批专用 Adapter 范围（用户已确认）：仅 Antigravity、OpenCode。** M2.5 首版不开发 Cursor、VS Code / Copilot、Cline 或其他产品的专用 Adapter；这些产品只列入后续候选评估，不代表首版支持。

所有专用 Adapter 必须默认仅操作当前 Windows 用户级配置。项目级和系统级配置可以检测并提示，但不得自动修改。未来如果某一客户端不提供可安全识别的全局配置位置，Adapter 必须拒绝猜路径并退回手动接入。

### 4.2 Generic / Manual（通用手动接入）

没有专用 Adapter，但兼容性通过的 MCP Client，可通过 GUI 的“添加通用 MCP Client”注册：
1. 用户输入显示名称，选择或确认“通用 MCP Client”类型；
2. AirBridge 创建独立 Agent 实例、凭据和 Resource Audience；
3. Supervisor 为其准备独立 Worker / endpoint；
4. GUI 生成 Streamable HTTP endpoint、OAuth 授权说明和配置片段；
5. 用户将配置粘贴到第三方客户端自己的 MCP 设置中；
6. 用户在第三方客户端发起 OAuth 授权；
7. AirBridge 根据实际认证请求与 MCP 协议健康检查确认连接。

Generic / Manual 模式不得扫描或修改未知客户端的配置目录，不尝试读取客户端私有 Token Vault，也不得伪造客户端授权完成状态。

### 4.3 Unsupported（暂不支持）

以下客户端不得被显示为“已支持”：
- 仅支持 stdio，且无法使用 AirBridge 受管 HTTP 模式的客户端；
- 无法通过 HTTPS 验证 Gateway Resource Server 证书的客户端；
- 不支持 Gateway 所需 MCP OAuth / Resource Metadata / Token Audience 行为的客户端；
- 需要以明文 Service Token、无认证 HTTP 或关闭 TLS 验证才能接入的客户端。

不允许为了增加客户端数量而退回无认证 HTTP、把 M2.4 Agent Service Token 写入第三方配置，或共享不同 Agent 的凭据。

## 5. Adapter 接口职责

专用 Adapter 只负责客户端配置集成，不负责启动或实现 Gateway Worker。建议的逻辑接口如下（名称为架构示意）：

| 方法 | 作用 |
|---|---|
| `detect_installation()` | 检测产品安装和版本；不根据目录猜测身份 |
| `locate_user_config()` | 定位当前 Windows 用户级 MCP 配置 |
| `inspect_config()` | 检查格式、配置层级、重复项和覆盖关系 |
| `build_server_entry()` | 生成该客户端要求的 MCP Server 配置项 |
| `apply_managed_entry()` | 备份并安全合并 AirBridge 管理项 |
| `verify_managed_entry()` | 重新读取并确认写入结果 |
| `remove_managed_entry()` | 只删除带有明确所有权标记的 AirBridge 项 |
| `launch_auth_flow()` | 可选：调用该客户端公开支持的 OAuth 命令 / 打开设置 UI |

Adapter 必须能够在“不写入配置”的只读模式下完成检测。任何配置文件解析失败、存在不确定的冲突、格式未知或无法安全保留用户数据的情况，都必须停止自动写入。

通用 Worker 不应依赖上述 Adapter 接口；Adapter 故障不得影响 AirBridge Runtime、串口通信或其他 Agent Worker。

## 6. 注册表与分发策略

M2.5 首版建议将内置 Adapter 随同 AirBridge.exe 打包，使用本地、版本化、可测试的 Registry。暂不允许从任意 URL 动态下载或执行第三方 Python Adapter。

客户端类型描述至少包含：
- type ID、显示名称、Adapter ID 和版本；
- 支持的客户端版本范围；
- 配置能力（自动配置 / 手动配置）；
- 当前用户级配置路径解析策略；
- MCP 传输能力；
- OAuth / Client Registration 兼容要求；
- 是否支持程序化授权入口；
- 适配器测试版本和验证状态。

以后若需要第三方可插拔 Adapter，必须另行设计签名、来源信任、版本约束、权限隔离、更新和回滚机制；不能把任意 Python 文件作为插件直接加载。

## 7. GUI 添加 Agent 流程

建议 GUI 提供统一入口：

```text
Agent 管理
  └─ 添加 Agent
       ├─ 选择已知客户端
       │    ├─ Antigravity
       │    ├─ OpenCode
       │    └─ 其他专用 Adapter（后续版本评估，不属于 M2.5 首批）
       └─ 通用 MCP Client（手动配置）
```

向导步骤：
1. 选择客户端类型或通用接入；
2. 检测客户端版本与兼容能力；
3. 设置 Agent 显示名称；
4. 创建唯一 Agent 实例身份和默认只读 Scope；
5. 初始化独立 Service Credential；
6. 分配独立 HTTPS Resource Server endpoint；
7. 专用 Adapter 写入当前用户配置，或 Generic 模式展示配置片段；
8. 用户在 Agent Host 内完成 OAuth 授权；
9. 验证 MCP initialize、tools/list 和只读测试；
10. 用户明确启用该 Agent Worker。

全局 Gateway 默认 OFF 时，添加 Agent 只会建立配置，不会自动启动 Worker；用户完成配置并显式打开 Gateway 后才能启动。是否在 Agent 添加向导中自动激活其 Agent 开关，仍需单独定义。

## 8. 可扩展性与安全边界

- Worker、OAuth Broker、Token Introspection、Agent Security 与 Host Adapter 分层；Host Adapter 不接触 Service Token 或 OAuth Token。
- 每个 Agent 实例使用独立 Worker / 身份 / Credential / Grant / Resource Audience / Scope。
- MCP Host 自己完成 OAuth 授权和 Token 存储；AirBridge 不读取客户端 Token Vault。
- MCP Resource Server 仅监听 loopback，且携带 Bearer Token 的请求必须经 HTTPS。
- OAuth Resource Metadata 中的 Audience 必须绑定到具体 Agent 实例，不能跨实例共享。
- CIMD / DCR 必须使用受控注册策略；不得因为增加一个 MCP Client 就开放任意 Metadata URL fetch。
- 配置 Adapter 只修改当前用户级配置，不修改项目级和系统级配置。
- 配置写入必须备份、原子合并、保留无关键值；未知格式失败关闭。
- 新 Adapter 通过独立契约测试，不得以客户端品牌判断 Agent 权限。

## 9. 候选客户端与兼容性评估

当前官方文档显示，以下产品具备不同程度的远程 MCP 接入能力。它们只是候选，不代表已通过 AirBridge OAuth / TLS / Worker PoC：

| 候选客户端 | 官方资料可确认的能力 | AirBridge 后续工作 |
|---|---|---|
| Cursor | 支持 Streamable HTTP 与 OAuth；支持全局 / 项目配置，并提供程序化注册 API | 开发 Cursor 专用 Adapter；测试 Desktop 与其他运行表面 redirect URI 差异 |
| VS Code / GitHub Copilot | 当前 Copilot MCP 配置支持 HTTP；OAuth 字段由客户端处理 | 明确 Copilot Harness 与旧 Local Harness 的配置边界，再实现 Adapter |
| Cline | 支持远程 Streamable HTTP 和 OAuth 授权流程 | 验证当前版本、配置写入方式及授权行为，再实现 Adapter |
| Continue | 官方配置文档包含 Streamable HTTP MCP Server 类型 | OAuth / Resource Metadata / Token Audience 兼容性未确认；先做 PoC，不得仅凭 transport 字段宣称可用 |

## 10. 分阶段落地建议

**M2.5 首版：**
- 建立客户端类型注册表和稳定 Agent 实例 ID；
- 首批只实现 Antigravity / OpenCode 两个专用 Adapter；
- Generic / Manual 通用接入入口是否纳入首版，保留为独立待决策项；
- Worker / Credential / OAuth Grant / Resource Audience 按 Agent 实例隔离；
- 不实现在线插件下载或任意第三方 Adapter 执行。

**后续版本（不属于 M2.5 首批范围）：**
- 根据实际需求与兼容性 PoC，评估并逐步增加 Cursor、VS Code / Copilot、Cline 等专用 Adapter；
- 为每种 Adapter 建立版本矩阵和自动化契约测试；
- 只有在确有第三方开发者生态需求时，才评估签名插件机制。

## 11. 验收条件

- [ ] 新增一个 Agent 类型无需修改 Gateway Worker 核心协议和 OAuth Broker 核心逻辑。
- [ ] 同一客户端可以注册多个独立 Agent 实例。
- [ ] 每个实例具有不同 Agent ID、Credential、OAuth Grant / Resource Audience / Scope 和 Worker 状态。
- [ ] Generic / Manual 模式可生成完整配置片段和 OAuth 操作指引，但不修改未知客户端配置。
- [ ] 专用 Adapter 只能修改当前用户级配置；项目级 / 系统级配置保持不变。
- [ ] Adapter 写入失败、配置格式未知或发现冲突时安全停止，不覆盖用户配置。
- [ ] 客户端 Token Vault 不被读取、复制、修改或删除。
- [ ] 不符合 Streamable HTTP / HTTPS / OAuth 安全要求的客户端无法启用受管 Gateway Worker。
- [ ] M2.5 首批专用 Adapter 仅包含 Antigravity 和 OpenCode。
- [ ] 新增 Adapter 具有版本兼容性测试、配置回归测试和 OAuth/TLS 真实客户端测试。
- [ ] GUI 关闭时，所有 Agent Worker 按用户确认的生命周期策略停止，不留下孤儿进程。
