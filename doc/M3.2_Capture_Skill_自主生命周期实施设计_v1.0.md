# M3.2：Capture Skill 自主生命周期实施设计

- 文档编号：AB-M3.2-CAPTURE-001
- 版本：1.0
- 日期：2026-11-18
- 状态：**实施设计；尚未开始运行代码迁移**
- 架构依据：[ADR-006：专业软件生命周期由 Agent Skill 自主掌握](ADR-006_Skill自主掌握专业软件生命周期.md)
- 审计代码基线：`163798fced2b861d9d213f7a35af929a24cc9730`

> 本文把 Capture Skill 的职责和迁移任务具体化。它不是对 AirBridge Core 增加 Capture API 的提案，也不代表 Skill 已完成实现或 Host B 实机验收。任何真实 Capture 启动、设计打开、保存或退出仍须由用户明确授权。

---

## 1. 目标与非目标

### 1.1 目标

建立一个独立的 **OrCAD Capture Skill**，让它通过通用 AirBridge HTTP API 自己控制 Host B 上的 Capture 17.2：

- 版本与安装目录选择；
- 进程状态检查、启动和会话归属识别；
- Tcl Bridge 文件部署、capAutoLoad Hook 安装和 READY 核验；
- 持久 Tcl Interpreter 请求提交、结果回收、超时和 UNKNOWN 处理；
- DSN / OPJ 打开、活动 Design / Schematic / Page 查询；
- 设计修改、保存策略和结果验证；
- Capture 自身的正常退出，以及退出后进程确认；
- 发生弹窗、进程归属不明、保存状态不明、Bridge 状态不明时安全停止并报告。

### 1.2 非目标

本阶段不做以下事情：

- 不新增 `CaptureAgent.exe`、Host-B 专用 AirBridge 服务或另一套通信程序；
- 不在 AirBridge Core 中新增 Capture 专属 HTTP 路由、ABFP 帧或生命周期配置；
- 不让 AirBridge 自己扫描 Cadence 版本、启动 Capture、原生打开 DSN 或发送 WM_CLOSE；
- 不将 Dbo API、Capture 对象模型、PDF 导出逻辑或保存策略迁入 AirBridge；
- 不自动关闭用户手动启动的 Capture，不自动丢弃未保存设计；
- 不在本阶段删除旧 `CaptureTclAdapter`、`CaptureTclRuntimeManager`、`EDAExecutor` 或旧 EDA 帧。

## 2. 与 AirBridge 的边界

Host A 与 Host B 仍运行同一个 `AirBridge.exe`。Capture Skill 位于 Host A 的 Agent 环境；Tcl Bridge 和专业辅助脚本作为 Skill 管理的载荷，运行在 Host B 的 Capture Tcl Interpreter 内。

| 能力 | 所有者 | 接口 / 载荷 |
|---|---|---|
| A/B 串行通信、ABFP、认证、审计、去重 | AirBridge Core | 既有通用协议与 Agent Security |
| 在 B 执行 PowerShell、检查 PID、启动 GUI | Capture Skill 决策；AirBridge 提供执行能力 | `POST /api/v1/shell/exec` |
| 在 B 读写工作文件、部署 Hook、交换 Request / Result | Capture Skill 决策；AirBridge 提供文件操作 | `POST /api/v1/fs/*` |
| Capture 版本选择、实例复用或拒绝策略 | Capture Skill | Skill 配置与版本规则 |
| Tcl Bridge、capAutoLoad Hook、Session / Request / Result 协议 | Capture Skill | Skill 自有 Tcl 文件和工作目录 |
| Dbo / Project Manager / Schematic / Page 专业 API | Capture Skill | 显式 source 的 Skill Helper |
| 打开 DSN、保存、退出、结果判断 | Capture Skill | Tcl 请求与 Shell 进程核验 |
| PDF、BOM、网表等具体业务 | 对应专业 Skill | 调用 Capture Skill 的会话能力 |

Skill 不直接访问串口，不把 Host B 文件路径当成 Host A 本地路径，也不通过沙箱文件系统模拟远端文件操作。

新 Skill 只调用通用 Shell / RFS / 文件传输 API。禁止依赖 `/api/v1/eda/versions`、`/api/v1/eda/execute`、`target_file` 或 `keep_open` 来完成新工作流。

## 3. 建议目录结构

首期采用仓库内可独立复制的 Skill 包：

```text
skill/
├── airbridge/                    # 通用远程通信 Skill，不含 EDA 业务流程
├── orcad-capture/                # Capture 生命周期与专业 API Skill
│   ├── SKILL.md
│   ├── scripts/
│   │   ├── capture_session.py    # Host A：会话编排、Shell / RFS 调用
│   │   └── airbridge_client.py   # Host A：Bearer、HTTP、状态与错误处理
│   ├── assets/
│   │   ├── bridge/
│   │   │   └── capture_bridge.tcl
│   │   └── tcl/
│   │       ├── common_helpers.tcl
│   │       └── dbo_helpers.tcl
│   └── references/
│       ├── capture-17.2-runtime.md
│       └── dbo-api-notes.md
└── orcad-pdf-export/              # 专项 PDF 业务 Skill
    ├── SKILL.md
    ├── scripts/
    └── references/
```

说明：

- `orcad-capture` 是唯一掌握 Capture 会话生命周期的 Skill。
- `orcad-pdf-export` 只负责 PDF 导出业务；它通过 Capture Skill 的会话能力提交 Tcl 工作流，不再创建第二套启动 / Bridge / 关闭机制。
- 后续 Capture 查询、属性编辑、BOM、批量导出等 Skill 也复用同一个 `orcad-capture` 会话能力。
- Skill 对 AirBridge HTTP 的封装只放在 Skill 自己的代码中；不复制 AirBridge 的串口、ABFP、Token 数据库、RequestTracker 或 Agent Security 实现。
- 如果 Agent 平台不支持跨 Skill 程序导入，安装说明必须把 `orcad-capture` 作为依赖一起安装；专项 Skill 通过平台支持的 Skill 调用机制委托，不得复制生命周期实现。

## 4. Capture 会话状态机

首期采用 Skill 管理的明确状态，不将 AirBridge Request 状态与 Capture 会话状态混为一谈：

| 状态 | 含义 | 允许的下一步 |
|---|---|---|
| `absent` | 没有本 Skill 创建的活动会话 | 发现进程或启动 |
| `inspecting` | 正在核对 Capture 进程、路径和版本 | 得到安全结论或停止 |
| `starting` | 已提交 Capture 启动命令，正在确认 PID | 等待进程 / READY |
| `bridge_pending` | Capture 进程存在，但本会话 Bridge 尚未 READY | 等待、诊断或 UNKNOWN |
| `ready` | Session ID、Nonce、PID、Tcl 版本均已核验 | 执行 Tcl 请求 |
| `busy` | 当前 Session 有一个未终结请求 | 只等待当前请求；不并发提交 |
| `closing` | 已提交 Skill 定义的关闭请求 | 等待 Capture 进程退出 |
| `closed` | Capture PID 已确认退出 | 保留审计记录，可创建新 Session |
| `failed` | 有明确失败证据 | 诊断或按规则恢复 |
| `unknown` | 不能确定远端是否执行 / 进程是否退出 | 禁止盲目重试或强杀，先查询 / 人工处理 |

Skill 为每次 Capture 会话生成独立 Session ID 和高熵 Startup Nonce。Session Manifest 至少记录：

- Session ID、Nonce；
- 选择的 Capture 版本、`capture.exe` 完整路径；
- 启动 PID、进程启动时间；
- capAutoLoad Hook 路径；
- Bridge 工作目录、READY 记录；
- 最近请求 ID、Payload SHA-256、结果状态；
- 会话关闭状态和诊断信息。

PID 不是稳定身份。每次复用或关闭前，Skill 都要重新查询进程，核对 PID、映像路径和启动时间，降低 PID 重用导致误操作的风险。

## 5. 软件发现、启动与实例策略

### 5.1 版本选择

版本发现属于 Capture Skill。首期不要照搬 Core 的隐式 `version=auto` 行为。优先从 Skill 显式配置读取版本和程序路径；需要扫描时，由 Skill 提交只读 PowerShell 命令，解析 Host B 返回的安装信息，并按 Skill 自己的兼容策略选择版本。

Capture 17.2 首期配置需包含：

- `capture.exe` 绝对路径；
- 对应的 `capAutoLoad` 目录；
- 预期 Capture 版本标识；
- 预期 Tcl 版本（现场基线为 Tcl 8.6.0）；
- 需要的环境变量和工作目录。

不能仅凭目录名就认定安装有效；启动后仍需核验实际进程映像路径和 Bridge 报告的运行时版本。

### 5.2 已有进程策略

Capture 17.2 是单实例应用，不能用“发现 Capture.exe 就复用”作为充分条件。

- 若已存在与 Skill Manifest 完全匹配且 Bridge READY 的本 Skill 会话：可以按 Session ID 复用。
- 若存在用户手动启动的 Capture、其他版本 Capture、身份无法核实的 Capture，或有未保存状态风险：停止自动启动，不向其注入 Hook，不自动关闭；要求用户确认处理。
- 若存在上一次本 Skill 创建的实例但 Bridge 状态不明：先按 PID / 路径 / 启动时间核验，再尝试只读诊断；不得同时再启动第二个 Capture。
- 不得为了让自动化“继续”而关闭所有同名进程。

只有用户明确授权后，Skill 才可调用自己定义的正常关闭工作流来处理一个已识别的旧会话；未经授权不能执行关闭。

### 5.3 启动命令

Skill 通过通用 Shell 提交短时 PowerShell 命令，使用 `Start-Process -PassThru` 启动 Capture 并返回 PID。Shell 命令不能同步等待 GUI 进程退出。

启动后，Skill 用新的只读 Shell 请求反复核验：

- PID 对应进程存在；
- `ExecutablePath` 与配置路径一致；
- 进程启动时间与新会话记录一致；
- 未出现启动失败 / 许可 / 迁移 / 缺库等需要人工处理的弹窗。

进程存在只表示进程已经创建，不表示 Capture GUI 初始化或 Tcl Bridge 已可用。

## 6. Tcl Bridge 部署与所有权

### 6.1 文件与 Hook 所有权

`capture_bridge.tcl`、Tcl Helper、Hook、Request / Result 文件格式和生命周期全部由 Capture Skill 维护。它们不能继续由 AirBridge 的 `CaptureTclRuntimeManager` 或通用 Core 自动生成和管理。

建议每个会话使用独立工作目录，例如：

```text
%LOCALAPPDATA%\AirBridgeSkills\Capture\sessions\<session-id>\
    bridge.tcl
    bridge.ready
    session.manifest
    requests\
    running\
    results\
    logs\
```

目录由 Skill 通过 RFS / Shell 创建，不假设固定盘符或 `E:\\_airbridge_temp` 必然存在。

### 6.2 capAutoLoad Hook

Skill 为每个 Session 生成唯一 Hook 文件名，例如：

`ab_skill_<session-id>.tcl`

Hook 只负责：

1. source 本 Session 的 Bridge 文件；
2. 启动本 Session 的 after 轮询；
3. 创建带 Session ID / Nonce / PID / Tcl 版本的 READY；
4. 返回 Capture 事件循环，不阻塞启动。

安全规则：

- 不覆盖 Capture 安装目录里现有的 Cadence Tcl 文件或其他用户文件；
- 不替换整个 capAutoLoad 目录；
- 只删除由当前 Session Manifest 记录且内容 Hash 匹配的 Hook；
- 若写权限不足，报告所需权限并停止，不自动提权；
- 清理失败时保留记录并报告，不扩大删除范围。

### 6.3 READY 验证

READY 不是单纯的文件存在标记。Skill 至少校验：

- schema 版本；
- Session ID 完全匹配；
- Startup Nonce 完全匹配；
- runtime PID 与 Shell 查询到的 PID 一致；
- Tcl 版本在 Skill 允许范围；
- Bridge 文件版本 / Hash 与本 Skill 发出的版本一致。

任何字段不匹配均视为启动失败或 UNKNOWN，不能继续提交专业脚本。

### 6.4 请求与结果协议

沿用已实测 Bridge 的安全机制，但协议资产迁归 Capture Skill：

- UUID Request ID；
- Session ID 与 Startup Nonce 绑定；
- Payload SHA-256；
- 原子文件提交，避免读取半写入请求；
- requests / running / results 分区；
- 单 Interpreter 请求串行执行；
- 输出、错误栈、执行时长、PID、Tcl 版本和结果状态；
- 超时后查询同一 Request ID，不能无条件生成新 ID 重跑；
- 结果保留与清理仅作用于当前 Session 目录；
- 不能将文件缺失或通信中断自动解释为请求未执行。

Bridge 只负责脚本投递、执行和回执，不在 Bridge 中放置 Dbo API 工作流或 PDF / BOM 等业务逻辑。

## 7. Tcl 专业辅助函数与 Dbo API

### 7.1 显式加载 Helper

AirBridge 的 `ORCAD_TCL_POLYFILL` 不再作为新 Capture Skill 的隐式依赖。原先由 Core 注入的辅助函数应显式迁入 Capture Skill 的 Tcl 资产，按职责拆分：

- Bridge 基础函数：只负责请求解析、结果写回和会话状态；
- Capture 通用 Helper：如 Dbo NULL 判断、CString 转换等；
- 业务 Helper：只由对应专业 Skill 自己 source。

每个请求必须明确 source 所需的 Helper，或由本 Session Bridge 在 READY 前 source 固定的 Skill Helper。不能依赖 EDAExecutor 在脚本前插入一段不可见代码。

### 7.2 Dbo API 归属

以下专业内容只归 Capture Skill：

- DboSession / DboDesign / DboSchematic / DboPage 对象模型；
- GetActiveDesign、GetDesignAndSchematics、NewPagesIter 等具体 API；
- CString、DboState、迭代器构造与释放；
- 版本差异、只读 / 写入副作用分类；
- Start Page、SchematicView 等 GUI 上下文要求；
- 打开工程、页面切换、元件查询、属性读取和修改；
- 保存和业务结果判断。

《Capture Dbo API Tcl 示例索引 v1.0》作为研究资料迁入该 Skill，不再作为 AirBridge Core / Adapter 接口文档。

## 8. 打开、保存与关闭的安全工作流

### 8.1 打开 DSN / OPJ

Capture Skill 在 Bridge READY 后，提交经过校验的 Tcl `Open` 请求打开用户指定的 DSN 或 OPJ。不要使用 AirBridge 的 `target_file` 原生命令行参数，也不要由通用 Core 自动拼接 Tcl `Open`。

打开后，Skill 必须通过专业 API 核验：

- 活动 Project / Design 存在；
- 活动 Design 对应用户选择的工程；
- 必需的 Schematic / Page 可查询；
- 没有把上一个工程的 Active Design 当成本次打开成功。

打开命令返回成功但 Active Design 不匹配，仍然是业务失败。

### 8.2 保存策略

是否保存由用户指令和专业 Skill 工作流共同决定。Skill 必须把以下状态区分开：

- 只读操作：不应触发保存；
- 已修改且用户已授权保存：调用 Capture 自身保存流程，再检查保存结果；
- 已修改但没有保存授权：停止在需要用户决定的状态；
- 保存结果不确定：保留现场、查询同一请求 / 文件状态，不自动重复执行；
- 出现 Save / Save As / 库迁移等对话框：不模拟按键，不自行选择覆盖或丢弃。

### 8.3 正常退出

Capture Skill 自己提交 Capture Tcl `Exit`。由于 `Exit` 会终止 Tcl Interpreter，关闭请求应采用两阶段协议：

1. Bridge 先写入一个可查询的 `close_accepted` 结果并停止接受新请求；
2. 通过事件循环安排 Capture `Exit`；
3. Host A Skill 使用通用 Shell 持续查询原 PID；
4. 只有确认 PID 对应进程已经退出，Session 才进入 `closed`；
5. 如果进程仍在、出现保存提示或查询超时，状态保持 `closing/unknown`，报告用户并保留日志 / Manifest。

不得把 AirBridge `EDA_APP_CLOSE`、`ProcessSupervisor.close_owned_process("capture")` 或 `keep_open=false` 当作新 Skill 的正常关闭接口。

## 9. 最小权限与通用 API 使用

Capture Skill 使用预配置 Bearer Token；Token 不写入仓库、Bridge 文件、PowerShell 命令行参数、Request / Result 文件或日志。

首期最小 Scope：

| Scope | 使用目的 |
|---|---|
| `shell.execute` | 检查进程、启动 Capture、查询 PID / 路径、等待退出 |
| `shell.read` | 若单独提供 Shell 任务只读查询 |
| `filesystem.read` | 读取 READY / Result / Manifest / 日志、检查文件 |
| `filesystem.write` | 创建目录、上传 Hook / Bridge / Request 文件、清理本 Skill 文件 |
| `request.read` | 可选：按 Request ID 查询同一通用 Shell / 查询请求记录 |

不申请 `eda.execute`，不使用 EDA 专用路由。只读操作不得因复用一个 POST HTTP 方法而误申请 `filesystem.write`；RFS 的 Scope 按实际文件操作分类。

## 10. 与 orcad-pdf-export 的集成

PDF Export Skill 只负责：

1. 收集 DSN、输出目录、PDF 文件名、Ghostscript 与 PostScript Printer 参数；
2. 检查输出文件是否存在，按照用户明确的覆盖授权处理；
3. 请求 Capture Skill 建立 / 获取 Capture Session；
4. 通过 Capture Skill 的 Tcl 执行能力提交 PDF 导出脚本；
5. 检查 PDF 结果 Marker、文件签名、大小和 Ghostscript 验证结果；
6. 将业务结果返回用户；
7. 根据调用策略请求 Capture Skill 关闭会话，或保留会话供用户继续操作。

它不再负责或依赖：

- `/api/v1/eda/versions`；
- `/api/v1/eda/execute`；
- `target_file` / `keep_open`；
- AirBridge 自动启动 Capture；
- AirBridge 自动打开 DSN；
- AirBridge 注入 Polyfill；
- AirBridge 自动 WM_CLOSE；
- 共享的 `_cadence_stdout.log` / `_bootstrap.tcl` 生命周期。

导出模板中的 `is_dbo_null` 等函数必须显式 source Capture Skill Helper，不能依赖 `EDAExecutor` 注入 Polyfill。

## 11. 从现有代码迁移的对应关系

| 现有实现（基线 163798f） | 当前职责 | 迁移目标 |
|---|---|---|
| `CaptureTclBridgeSession` | Bridge Session 文件协议、Nonce、READY、Request / Result、Hash、UNKNOWN | 拆为 Skill 自有 Tcl Bridge 资产与 Host A Python 编排；AirBridge 不再构建 Session |
| `CaptureTclRuntimeManager.ensure_session()` | Cadence 发现、进程独占关闭、安装选择、Hook 写入、Capture 启动、READY | 逻辑迁入 `orcad-capture` Skill；只保留经验证的纯协议知识 |
| `CaptureTclRuntimeManager.close_session()` | 用 ProcessSupervisor 关闭受管 Capture | Skill 用 Tcl `Exit`，再用通用 Shell 确认进程退出 |
| `CaptureTclAdapter` | 将 EDA 请求映射到 Capture Session，并按 `target_file` 自动执行 `Open` | 新 Skill 不调用；旧 EDA 兼容路径保留至 M3.5 |
| `eda_engine.ORCAD_TCL_POLYFILL` | 隐式向专业脚本注入 Capture Helper | 显式迁为 Skill Helper；删除注入前先更新全部调用者 |
| `CadenceVersionManager` | 在 Core 代码中发现 / 选择 Cadence 安装 | Capture Skill 自主实现和配置版本选择 |
| `ProcessSupervisor.DEFAULT_SPECS["capture"]` | Core 内置 Capture 进程身份和关闭策略 | 新 Skill 自己查询并核验 PID / 映像；保留旧兼容进程监督，直至调用者迁完 |
| `skill/orcad-pdf-export` | 调用 EDA API，依赖 Core 启动、开图、关闭 | 改为调用 `orcad-capture` 的生命周期能力 |

**禁止将旧类只换个包名就算迁移完成。** 目标是让专业软件决策和状态机的调用入口真正位于 Skill，AirBridge 只保留与应用无关的 Shell / RFS / 协议传输。

## 12. 分阶段实施和验收

### M3.2.1：Capture Skill 包与会话模型

- 创建 `skill/orcad-capture`；
- 定义配置、Session Manifest、状态机、错误和 UNKNOWN 规则；
- 加入通用 AirBridge HTTP Client，支持 Bearer、超时、JSON 校验；
- 不修改现有 Adapter / EDAExecutor。

验收：Skill 能通过 Mock HTTP 测试运行状态机，权限不足和远端不可达时 fail-closed。

### M3.2.2：迁出 Bridge 文件协议

- 将已验证的 Session / Nonce / READY / Request / Result / Hash 机制迁入 Skill 的 Tcl 资产；
- 为 Hook 使用唯一名称，只能清理自己的 Hook；
- 让 Host A 编排通过 RFS 部署、读取、提交和取回结果；
- 添加重复 Request ID、Payload Hash 不匹配、半写入文件、过期结果和会话错配测试。

验收：Python / Tcl 模拟器下多条 Tcl 请求串行执行并返回可关联结果；错误和 UNKNOWN 不误报成功。

### M3.2.3：Skill 自主启动与 READY

- Skill 自己进行版本与进程发现；
- 明确已有实例策略，保护手动 Capture 和未保存工程；
- 用通用 Shell 启动目标 `capture.exe`；
- 等待并严格核验 READY。

验收：Windows Hosted CI 覆盖进程路径核验、PID 复用、版本不匹配、启动失败和 READY Nonce 错配；真实 Capture 17.2 现场确认一次启动和 READY。

### M3.2.4：Tcl 请求 / 结果队列

- Capture Skill 通过 generic RFS / Shell 使用 Session 独立文件队列；
- Tcl Bridge 轮询、原子认领 Request、执行一次并发布 Result；
- 请求、结果按 16 KiB 限制分块，以适配当前单帧 RFS；
- UNKNOWN 只能依据原 Request ID 查询结果，不自动重发。

验收：Windows Hosted CI 覆盖 Python 3.10 / 3.11 / 3.12；Tcl 8.6 解释器验证 Bridge 文件队列、串行请求、重复 Request ID、分块传输及结果完整性。

### M3.2.5：OPJ 打开与 Dbo 只读查询

- 仅支持用户明确选择的绝对 Host-B `.opj` 路径；通过 generic Shell 做远端文件存在性 / 类型 / 长度预检；
- Open 前先读取当前 Active Design；已有活动 Design 时拒绝切换或接管；
- Open 命令要求显式用户授权，并与 Dbo Active Design / Project Manager 身份校验放在同一个原始 Request ID 中；
- 验证 Dbo `GetActiveDesign` 与 `GetActivePMDesign` 指向同一对象，并匹配 READY Session 记录的 Capture PID / Tcl 版本；
- DBO-V02 只枚举当前 Session 已加载的 Design / Library，按样例释放迭代器和 DboState；
- 不调用 `GetDesign` / `GetLib` 等可能加载对象的 API，不保存、不编辑、不移除对象。

验收：Hosted CI 使用 Tcl 8.6 解释器与 Mock Dbo wrapper 验证命令拼装、Base64 路径安全、活动对象身份比较、枚举结束和资源释放；真实 Capture 17.2 的 OPJ 打开及 Dbo 实测单独记录，不由 Hosted CI 代替。

### M3.2.6：设计关闭与退出

- 用户明确决定保存、丢弃或保留修改；Skill 不自行作出保存决定；
- 经单独授权后才允许发出 Tcl `Exit`；
- Exit 会终止 Tcl Interpreter，必须通过 generic Shell 的只读进程盘点确认原 PID 及启动时间对应进程确实退出；
- 退出结果不确定时保留 UNKNOWN，不强杀、不重复启动。

验收：真实 Capture 17.2 验证未保存提示、已保存工程正常退出、进程退出确认和新 Session 启动；不自动覆盖或丢弃用户设计。
