## 1. 目标与边界

本阶段在 Capture Skill 内实现显式授权的两阶段退出、原 Capture 进程退出确认、持久化退出意图、重复退出阻断及 UNKNOWN 安全处理。AirBridge Core 不增加 Capture 专用 Endpoint、ABFP Frame 或生命周期代码；远端 Tcl 仍通过 M3.2.4 通用请求/结果文件队列，进程检查仍通过通用 Shell。

本阶段不保存、覆盖、丢弃或修改设计，不处理/确认保存提示框，不发送 WM_CLOSE，不调用 taskkill / Stop-Process，不强杀 Capture。

## 2. 两阶段流程

### 阶段一：退出准备（只读）

CaptureExitCoordinator.prepare_exit(user_authorized=True)：

1. 要求 Session 为 READY 且显式授权；
2. 使用既有 Process Inspector 核验 PID、绝对映像路径、进程启动时间和文件版本；
3. 通过既有 Tcl Request Queue 读取 Tcl PID / Tcl 版本、Dbo Session 和当前 Active Design；
4. 报告 Active Design 是否存在及其名称；不调用保存或修改 API；
5. 将 Session ID、Startup Nonce、进程身份、准备 Request ID 和 Design 状态写入 Host A 本地原子 sidecar。

准备阶段不会关闭 Capture。发现身份不匹配、查询异常或结果 UNKNOWN 时 fail closed。

### 阶段二：安排退出并确认

CaptureExitCoordinator.request_exit(...) 必须同时收到：

- user_authorized=True：用户明确授权退出；
- design_saved_or_no_changes_confirmed=True：用户明确确认设计已保存或没有未保存修改。

执行顺序：

1. 获取与 Session Manifest 同目录的独占 Exit Lock，避免多个 Host-A 线程/进程并发安排 Exit；
2. 校验准备 sidecar 与当前 Session Manifest 的 Session ID、Nonce、PID、启动时间、映像路径、Capture / Tcl 版本完全一致；
3. 再次核验原 Capture 进程身份；
4. 在 Host A 本地先构造并验证 Exit 调度 Tcl 脚本，包括 PID、Session ID、Tcl 版本和延迟值；无效参数在此处被拒绝，不写入退出意图、不发送远端 Tcl 请求，也不把 Session 误标为 UNKNOWN；
5. 原子持久化 exit_scheduling 状态及唯一 Schedule Request ID；
6. 通过原有 Tcl Queue 发送延迟调度脚本：校验 Tcl PID / 版本后仅执行 after <delay> [list Exit]；
7. Tcl 脚本立即返回固定 Schedule Receipt；Bridge 先完成当前 Request 的结果发布，再回到事件循环处理延迟的 Exit 回调；
8. Host A 收到并严格核对原 Request ID 的成功结果后，先将 Session 转为 CLOSING 并持久化，再更新 sidecar 为 exit_scheduled；
9. 通过通用 Shell 只读进程盘点轮询，确认原 PID 已不存在；
10. 只有原 PID 不存在时，使用 ProcessExitEvidence 将 Session 标记 CLOSED 并持久化。

延迟值默认 1000 ms，可配置范围 250–10000 ms。它是 Tcl 事件循环调度缓冲，不是退出成功证据；唯一成功证据是 Host A 对原 PID 的独立只读盘点。

### 单快照进程身份核验

退出轮询的每一轮只获取一次 Capture 进程清单，并通过 assess_capture_processes(candidates, manifest) 使用该快照同时判断：

- 原 PID 是否仍存在；
- 进程映像路径是否与 Session 一致；
- 进程启动时间是否与 Session 一致；
- 文件版本是否与 Session 一致；
- 是否出现多个 Capture 实例或 PID 复用/身份不匹配。

不再先读取一次清单，再调用 Process Inspector 重新读取第二份清单做身份核验。这样避免 Capture 恰好在两次远程盘点之间自然退出时，第二次盘点返回“原 PID 已不存在”，却被误判为身份不匹配并进入 UNKNOWN。

回归测试 test_process_exit_between_inventory_snapshots_does_not_become_unknown 模拟第一份轮询快照仍有原 Capture、下一份快照中原 PID 已消失的竞态。预期是依据完整快照判断，最终 CLOSED，而不是误入 UNKNOWN。

## 3. Sidecar、请求队列门禁与并发保护

本地 Exit sidecar 路径为 Session Manifest 同目录下的 <manifest-name>.exit.json；辅助独占锁路径为 <manifest-name>.exit.json.lock。

- Exit 意图通过临时文件、flush / fsync 和原子 replace 持久化；唯一 Schedule Request ID 在发送远端请求前保存。
- Exit sidecar 同时保存 Exit Tcl 脚本的 SHA-256。恢复时将原 Request 结果中的 script_sha256 与该摘要比较，确保 Receipt 对应本次精确的 Exit 脚本。
- CaptureTclQueue.submit() 在发送任何普通 Tcl 请求前检查 Exit sidecar。状态为 prepared 时允许正常 Tcl 请求；状态为 exit_scheduling 时仅允许显式携带同一 Schedule Request ID 的原 Exit 请求通过。
- exit_scheduling、exit_scheduled、unknown、closed、格式损坏或 Session 身份不匹配的 sidecar 都会阻断新的普通 Tcl 提交；队列不会因为 Host A 重启而清除旧意图。
- Exit 成功回执后先持久化 CLOSING，再更新 exit_scheduled。若 Session 本地提交失败，则转 UNKNOWN；若辅助 sidecar 更新失败，也转 UNKNOWN 并保留原 Schedule Request ID。
- 若原 PID 已确认消失，Session CLOSED Manifest 是权威退出证据。之后仅辅助 sidecar 的最终写入失败，不得把已经确认的 CLOSED 改写成 UNKNOWN；此时报告“Session 已 CLOSED、sidecar 未最终完成”。
- Exit 锁采用 Host-A 进程内线程锁 + OS 内核文件锁，防止不同线程及不同进程并发 Exit / reconcile。锁文件可长期存在；锁的占用由操作系统维护，Host A 正常退出或崩溃后内核释放文件锁，后续只读协调不被旧的空锁文件阻塞。
- 若原 PID 已确认消失，Session CLOSED Manifest 是权威退出证据。之后仅辅助 sidecar 的最终写入失败，不得把已经确认的 CLOSED 改写成 UNKNOWN；此时报告“Session 已 CLOSED、sidecar 未最终完成”。

### 跨 Host-A 重启的只读退出协调

CaptureExitCoordinator.reconcile_exit(timeout_seconds=...) 只允许处理已有的 exit_scheduling / exit_scheduled / unknown / closed sidecar，不接受新的退出授权，也不调用 queue.execute()，绝不重新安排 Exit。

协调顺序：

1. 获取与 Exit 共用的线程锁 / 内核文件锁；验证 sidecar 与当前 Manifest 的 Session ID、Nonce、PID、启动时间、Capture / Tcl 版本一致，并校验原 Schedule Request ID；
2. 使用通用 Shell Process Inspector 执行只读盘点。只有盘点成功、输出完整有效时，才使用原 PID 是否存在作判断；
3. 若原 PID 已不存在，则用原 Session PID / start time 建立 ProcessExitEvidence，通过受控状态转换进入 CLOSING，再持久化 CLOSED。这个证据说明原 Session Capture 已退出，不声称一定是 Exit 调度命令导致退出；
4. 若原 PID 仍存在，必须核对映像路径、启动时间和文件版本。身份不匹配或多个实例进入 UNKNOWN；
5. 仅对仍存活且身份完全匹配的原 Capture，通过 CaptureTclQueue.read_result() 读取原 Schedule Request 的结果清单和结果分块。此 API 使用有界 RFS 读取并验证 Session ID、Nonce、Request ID、脚本 SHA-256、CRC 和结果内容；Exit 协调器还会比较 sidecar 保存的原始 Exit 脚本 SHA-256；不执行写入、不改变 Session 状态，也不要求原进程已经退出；
6. 只有读到完全匹配的成功 Schedule Receipt，才能将 BUSY / UNKNOWN / READY 等允许的恢复状态经专用 Exit 状态守卫转为 CLOSING，然后只读轮询原 PID；
7. 原回执尚不存在、无法读取或不匹配时，Session 保持 UNKNOWN。后续可再次调用 reconcile_exit() 查询同一个 Request ID；不重复提交、不重发 Exit。

UNKNOWN 状态下，只有原 PID 消失的可信盘点证据，或原 Schedule Receipt 与原进程身份的完整证据链，才允许状态前进。原有 CaptureSession.resolve_unknown_operation() 仍用于普通 Tcl 操作；Exit 使用单独的 begin_close_from_reconciled_exit()，不把 Exit 误恢复为 READY。

新增故障注入测试覆盖：Exit 调度已回执但 sidecar 状态写入失败；Session 已 CLOSED 但 sidecar 最终写入失败；遗留 exit_scheduling 意图；Exit Lock 防并发与锁文件跨进程释放；非原 Schedule Request ID 的队列请求被门禁拒绝；重启后原 PID 已消失时直接 CLOSED；PID 仍存活且原 Schedule Receipt 有效时恢复 CLOSING 并继续只读等待；PID 仍存活但 Receipt 缺失时保持 UNKNOWN；通用 Queue 的 read_result 只读且不要求 Capture 进程存活。

## 4. UNKNOWN / 不重试规则

- Schedule Request 传输异常、结果丢失、Receipt 不匹配：标记 UNKNOWN，保留原 Request ID，禁止再次发送 Exit。
- Exit 已安排但 Session 或 sidecar 本地状态提交失败：标记 UNKNOWN；不得再次发送 Exit。
- 退出超时、Shell 盘点异常、非成功 Shell 结果、截断数据或无效 JSON：标记 UNKNOWN；只允许后续只读核查，不重试 Exit、不强杀。
- 原 PID 仍存在但路径、启动时间或版本不匹配：视为 PID 复用/身份不确定，标记 UNKNOWN。
- 进程清单只有在 Shell 请求明确完成、退出码成功、输出未截断且 JSON 完整有效时，才可将空数组解释为原 PID 不存在。
- 进程列表中原 PID 已消失，即使另有不属于本 Session 的 Capture 实例，也只确认本 Session 原 PID 已退出，不触碰其他实例。
- Exit 过程中出现保存提示框时，本阶段不会自动确认；若进程未退出则超时进入 UNKNOWN。
- 本地 Exit 脚本参数校验失败属于发送前的本地输入错误：保留 READY 与 prepared sidecar，不生成 Schedule Request ID，不进入 UNKNOWN。

UNKNOWN 表示远端退出结果或本地持久化状态不能被完整证明。不得通过重复调用 Exit 来“试探”结果。
