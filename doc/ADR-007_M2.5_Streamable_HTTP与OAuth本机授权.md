# ADR-007：M2.5 Gateway Streamable HTTP 与本机 OAuth 授权

- 状态：**提议采用，安全原型验证前不冻结**
- 日期：2026-11-20
- 决策范围：M2.5 Managed Gateway transport / MCP Host authorization
- 关联：M2.3 Agent Security、M2.4 Zero-Touch Authentication、M2.5 架构设计

## 1. 背景

M2.1 / M2.2 当前采用 MCP stdio：Antigravity / OpenCode 各自启动 Gateway 子进程。该模式适合 MCP Host 管理进程，但无法直接满足 AirBridge GUI 统一启动、停止、重启、监控 Gateway 的要求。

M2.5 需要一个由 AirBridge GUI Supervisor 管理生命周期、可持续运行且可显示真实运行状态的 Gateway 服务。因此需要面向 MCP Host 的持久网络传输。

## 2. 官方兼容性核查（2026-11-20）

### 2.1 Google Antigravity

Google 官方 MCP 文档确认：
- 远程 MCP Server 使用 Streamable HTTP；
- 远程地址字段为 `serverUrl`（文档也允许 `url`）；
- 请求头可配置在 `headers`；
- 认证支持 OAuth 2.0 / PKCE、CIMD、DCR 和自定义 Header；
- Antigravity App 可通过 Customizations 页面查看/复制 MCP 配置文件路径；
- Antigravity CLI 的全局配置为 `~/.gemini/config/mcp_config.json`，工作区配置为 `<workspace>/.agents/mcp_config.json`；
- Antigravity 发布 Client ID Metadata Document：`https://antigravity.google/oauth/client-metadata.json`；IDE CIMD 支持要求 2.6.0 或更高版本。官方注册优先顺序为手动 client credentials、CIMD（若 AS metadata 声明支持）再到 DCR；AirBridge 不写入手动凭据，因此托管流程优先 CIMD，旧版本 / 不支持 CIMD 时使用 DCR 回退。
- Antigravity CIMD 回调 URI 为 `https://antigravity.google/oauth-callback`；AS 可以对该官方 Client ID Metadata URL 和 redirect URI 进行预登记 / allowlist，而不必抓取任意 URL。

官方资料：
- https://antigravity.google/docs/mcp
- https://antigravity.google/docs/ide-mcp

### 2.2 OpenCode

OpenCode 官方文档确认：
- 远程 MCP Server 使用 Streamable HTTP；
- 配置字段为 `mcp.servers.<name>.type="remote"` 和 `url`；
- OAuth 默认启用，支持 PKCE、CIMD 和 DCR。官方注册优先顺序为预注册 Client ID（若配置）、CIMD（当 AS 支持且未设置自定义 redirect_uri）再到 DCR；AirBridge 托管配置不写预注册凭据或自定义 redirect_uri，因此应启用 CIMD，不能使用时回退 DCR。
- OpenCode 发布 Client ID Metadata Document：`https://opencode.ai/oauth/opencode/client.json`。CIMD 的 loopback callback 规则按 OpenCode 文档 / RFC 8252 处理；设置自定义 `redirect_uri` 会使 OpenCode 回退 DCR。
- `oauth: false` 是关闭 OAuth、改用 Header 凭据的选项，不适合将 Agent Token 写入普通配置文件的 AirBridge 目标；
- 默认使用经典 MCP initialize 协议；只有明确需要更新版协议时才配置 `protocol`；
- 用户全局配置为 `~/.config/opencode/opencode.json(c)`；Windows 系统级配置目录为 `%ProgramData%\opencode`；还存在工作区配置。

官方资料：
- https://opencode.ai/docs/mcp-servers/
- https://opencode.ai/docs/config/

### 2.3 MCP Python SDK

当前仓库 `mcp_gateway/pyproject.toml` 固定 `mcp==2.3.0`，要求 Python `>=3.11`。

MCP Python SDK v2 文档确认：
- 可通过 `transport="streamable-http"` 运行服务器；
- SDK 支持 Resource Server 侧的 `TokenVerifier`、`AuthSettings`、Protected Resource Metadata 和 401 challenge；
- SDK 的 Resource Server 组件验证已有 Token，不负责用户登录、Consent Screen 或签发 Token；
- 新架构需要单独实现或集成标准 OAuth Authorization Server，不能误以为 MCP SDK 自动提供完整 OAuth Provider。

官方资料：
- https://py.sdk.modelcontextprotocol.io/run/

## 3. 决策

### D7-1：Managed Gateway 目标传输采用 Streamable HTTP

**提议采用。**

- Gateway Worker 由 AirBridge Supervisor 启停；
- 每个 Agent 使用独立固定身份的 Worker / endpoint；
- Endpoint 默认只绑定 loopback；
- GUI 显示实际 endpoint、端口、PID 和健康状态；
- 当前 stdio transport 在迁移期保留，不因新增 HTTP transport 而删除。

不选择旧 HTTP+SSE transport。Antigravity 官方远程 MCP 文档明确要求 Streamable HTTP；OpenCode 也明确将远程连接定义为 Streamable HTTP。

### D7-2：客户端 OAuth Token 与 Gateway→AirBridge Agent Token 是两种不同凭据

**必须分离，禁止复用。**

| 凭据 | 使用方向 | 管理位置 | 用途 |
|---|---|---|---|
| MCP OAuth Access Token | Antigravity / OpenCode → Gateway Worker | 由 MCP Host 的 OAuth 流程管理 | 证明本地 MCP 客户端已获准访问某个 Gateway Resource |
| M2.4 Agent Service Token | Gateway Worker → AirBridge HTTP API | Windows Credential Manager | Gateway 以固定 Agent ID 调用 AirBridge API |

约束：
- M2.4 Agent Service Token 永不写入 Antigravity / OpenCode MCP JSON、Header 配置、环境变量或命令行。
- Gateway Worker 只从 Credential Provider 获取与自身固定 Agent ID 对应的 Service Token。
- Worker 验证入站 MCP OAuth Token 后，才可调用对应 Agent 的服务端能力。
- OAuth Access Token 的 subject / client / resource / scope 必须与该 Worker 的授权绑定相符。
- 不允许客户端在 MCP tool 参数中指定 Agent ID、Scope 或下游 Bearer Token。

### D7-3：HTTP MCP 采用 OAuth 2.1 / MCP Authorization 规范，不允许无认证降级

**提议采用，HTTPS 部署路径为实施阻断项。**

至少要求：
- Authorization Code Flow + PKCE（S256）；
- Protected Resource Metadata；
- Authorization Server Metadata 或 OpenID Connect Discovery；
- 支持 CIMD 和/或 DCR，客户端注册必须绑定用户明确授权；
- 校验 `resource` / token audience，Token 只能用于对应 MCP endpoint；
- 精确校验 redirect URI、state、PKCE verifier 和授权码一次性使用；
- Access Token 短时有效；公共客户端 Refresh Token 按 OAuth 2.1 规则轮换；
- 撤销 Agent 或本地授权后，相关 Token 不能继续访问；
- 对每个 Worker / Agent 分别授权，不能让 OpenCode 自动继承 Antigravity 的身份或权限。

**重要协议约束：** MCP Authorization 规范要求 Authorization Server endpoints 使用 HTTPS；OAuth Bearer Token Usage（RFC 6750）要求客户端到受保护 Resource Server 的 Bearer Token 请求同样使用 TLS。M2.5 因此要求 OAuth Broker 与每个 MCP Worker Resource Server endpoint 均使用 HTTPS，并由客户端正常验证证书链。HTTP 仅可用于规范允许的 loopback OAuth redirect URI，不可用于携带 Access Token 的 MCP 请求。

**用户已确认的 Windows 证书信任策略：**
- 证书信任只在当前用户（CurrentUser）范围建立；不得写入 LocalMachine Root 或其他机器级信任存储区。
- 首次安装 / 初始配置时必须向用户说明用途和信任范围，并取得明确同意后才导入；不要求管理员权限。
- 用户拒绝导入或撤销信任后，托管 Streamable HTTP / OAuth HTTPS Gateway 不可用；不得忽略证书错误、关闭 TLS 校验或降级为无认证 HTTP。
- 用户拒绝证书信任不影响既有 stdio 兼容路径和 AirBridge Core / Runtime。

因此，在实现前必须通过 Windows 原型验证：
1. 本地 Authorization Server 和每个 Worker 如何提供受目标客户端信任的 HTTPS；
2. CurrentUser 证书信任能否被 Antigravity App / IDE / CLI、OpenCode 和系统浏览器共同识别；
3. 证书 SAN、私钥保护、更新、轮换、撤销、重装和卸载方式；
4. OAuth 登录 / 授权回调在两类客户端中的完整流程；
5. 用户拒绝或撤销证书信任时的 UI 状态与 fail-closed 行为。

不得使用临时自签名证书后忽略客户端证书错误；不得为了绕过证书问题将服务降级为无认证 HTTP。CurrentUser 证书写入成功不等于目标客户端信任验证通过。若 PoC 必须扩大到 LocalMachine Root 或要求管理员权限，视为当前方案 No-Go，必须提交新决策，不能由实现自行变更。

### D7-4：客户端配置不写入内部 Agent Service Token

建议由 GUI 自动写入纯 endpoint 配置，并触发 MCP Host 的标准 OAuth 授权流程。

Antigravity 远程配置结构示意（仅示意，必须由目标版本验证）：

```json
{
  "mcpServers": {
    "airbridge-antigravity": {
      "serverUrl": "https://localhost:38862/mcp"
    }
  }
}
```

OpenCode V2 远程配置结构示意：

```json
{
  "mcp": {
    "servers": {
      "airbridge-opencode": {
        "type": "remote",
        "url": "https://localhost:38863/mcp"
      }
    }
  }
}
```

以上结构采用本版本首个 Agent 实例的固定默认端口示意：Broker issuer 为 `https://localhost:38861/`，首个 Antigravity Resource Server 为 `https://localhost:38862/mcp`，首个 OpenCode Resource Server 为 `https://localhost:38863/mcp`。正式配置不得写入 M2.4 Agent Service Token；本机 TLS 证书和 OAuth 授权服务器仍须通过真实客户端验收。

### D7-5：固定端口与端口变更

**用户已确认的默认 TCP 端口：**

| 组件 | 默认端口 | 地址 |
|---|---:|---|
| Local OAuth Broker | 38861 | `https://localhost:38861/` |
| 首个 Antigravity Worker | 38862 | `https://localhost:38862/mcp` |
| 首个 OpenCode Worker | 38863 | `https://localhost:38863/mcp` |

端口管理约束：
- AirBridge HTTP API 的 `127.0.0.1:8888` 保持不变。
- 默认候选端口池为 `38801–38864`；IANA 当前登记快照将其列为 Unassigned（IANA User Ports 范围），但并非 AirBridge 保留端口，发布时须复核登记状态。目标 Windows 主机必须执行实际监听 / excluded / dynamic range 检查。
- Windows 默认动态客户端端口范围通常为 `49152–65535`，但可被修改；以目标主机当前 `netsh` 状态为准。
- 参考：IANA https://www.iana.org/assignments/service-names-port-numbers/；Microsoft https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting。
- Broker 与每个 Agent Worker 只监听 loopback；同一客户端的多个 Agent 实例也使用不同、持久化的端口。
- 冲突时明确显示端口及可获得的进程名称 / PID；Broker 冲突阻断 Managed HTTPS OAuth，单个 Worker 冲突只阻断对应实例。不得静默随机换端口。
- Worker 端口变化会改变 Resource URL / audience，必须更新 Protected Resource Metadata 和该 Agent 的当前用户级 MCP Client 配置，并要求重新 OAuth 授权。
- Broker 端口变化会改变 issuer / Authorization Server Metadata，必须更新 Worker 引用和 discovery，并要求客户端重新授权；旧 issuer Grant 不得复用。
- 配置写入前备份并原子更新；新端口或任何客户端配置更新失败时回滚，不得形成半迁移状态。SAN 不包含端口，但 hostname 必须继续为 `localhost` 并通过正常 TLS 验证。
- 升级安装保留已保存端口，不重置为默认值。

## 4. Agent 与 OAuth Client 的身份绑定

- 每个 Gateway Worker 在服务端固定一个 Agent ID，例如 `antigravity` 或 `opencode`。
- OAuth client_id 是 MCP Host 的 OAuth 客户端标识，不等价于 AirBridge Agent ID。
- DCR / CIMD 注册本身不等于已获得 Agent 权限。
- 用户必须通过 GUI 或 MCP Host 认可的授权流程确认：哪个客户端连接哪个 Agent Worker，以及允许的操作 Scope。
- 授权记录应绑定 worker/resource、client、Agent ID、scope 和有效期。
- 更换 Agent Worker endpoint 或 Agent ID 时必须重新验证授权绑定。

## 5. 为什么不能直接使用 Header Token

Antigravity 和 OpenCode 都提供自定义 HTTP Header 的能力，但将内部 M2.4 Agent Service Token 写入客户端 JSON 会违反 M2.4 Zero-Touch 凭据设计：
- Token 会落入普通配置文件和备份；
- 配置文件复制、同步或诊断导出可能泄露凭据；
- 无法由 AirBridge Credential Provider 单独控制客户端侧 Token 生命周期；
- 客户端配置管理器将接触并处理明文秘密。

因此，自定义 Header 只可用于不包含 M2.4 Service Token 的替代实验方案，且必须经过独立安全评审。

## 6. 保留 stdio 兼容

在 Streamable HTTP OAuth 本机 HTTPS 原型完成前，stdio 仍是已验收的兼容路径：
- 由 MCP Host 启动同一个 AirBridge.exe 的内部 stdio Worker 入口；
- 不创建第二种 EXE 或独立 Gateway 包；
- stdio 的信任边界是受信任的父进程，不能声称 HTTP TokenVerifier 为 stdio 提供了同样的保护；
- GUI 可以管理 stdio 配置和诊断，但其对 MCP Host 生命周期的控制能力有限，不能把 MCP Host 启动的进程误报为 GUI 独立启动的服务。

## 9. 2026-11-20 OAuth / HTTPS 与客户端交互补充（v0.2）

### 9.1 Resource Server endpoint 也必须使用 HTTPS

此前示例使用 loopback HTTP endpoint，仅能表达监听范围，不能作为承载 Bearer Token 的生产传输方案。根据 [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750)，使用 Bearer Token 访问 Protected Resource 时必须使用 TLS，客户端还必须验证 Resource Server 证书链。

M2.5 托管模式统一采用：
- OAuth issuer / authorization / token / metadata：HTTPS；
- 每个 Agent Worker MCP endpoint：HTTPS；
- OAuth loopback redirect URI：可按规范使用 localhost HTTP redirect；
- 其他 Authorization / Resource URL：不得使用明文 HTTP。

推荐稳定 URL 形式：
- `https://localhost:<antigravity-port>/mcp`
- `https://localhost:<opencode-port>/mcp`

端口分配与证书 SAN 需在 Windows PoC 中验证。

### 9.2 Antigravity / OpenCode 的实际授权操作

官方文档明确了两种客户端的不同授权交互：

**Antigravity App / IDE**
- 在 Customizations / Installed / MCP Servers 中找到 AirBridge Server；
- 点击 Authenticate；
- 完成客户端启动的浏览器授权；
- 按界面要求提交授权码；
- Antigravity 自己存储和刷新 Token。

官方说明 App / IDE 的 OAuth Token 存储由 Antigravity 自身管理（当前文档列出 `~/.gemini/antigravity/mcp_oauth_tokens.json`）。AirBridge GUI 不读取、备份、导出或修改该文件。

**OpenCode**
- 在 `/mcps` 页面选择 AirBridge Server 并登录；
- 或调用 `opencode mcp auth <server-name>`；
- OpenCode 自己管理 OAuth Credential，存储在项目配置之外。

AirBridge GUI 可以打开客户端或在检测到 CLI 后提供授权命令快捷入口，但不得伪称自己直接保存了客户端 OAuth Token。

官方资料：
- https://antigravity.google/docs/mcp
- https://antigravity.google/docs/ide-mcp
- https://opencode.ai/docs/mcp-servers/

### 9.3 GUI 的认证状态语义

必须拆分：
- MCP Server 配置已写入；
- OAuth Broker 中已有授权 Grant；
- Worker 最近观察到成功 OAuth Token 验证的请求；
- MCP initialize / tools/list / 只读调用健康。

Broker 已签发 Grant 不代表 MCP Client 当前仍保存有效 Token。只有 Worker 真实收到并验证客户端请求后，才能更新“最近成功认证”时间。客户端 Token 文件始终由客户端自己管理。

### 9.4 CIMD 白名单优先与 DCR 兼容回退（D-07，用户已确认）

M2.5 首批只接受以下两个精确的官方 CIMD Client ID Metadata URL：
- Antigravity：`https://antigravity.google/oauth/client-metadata.json`。
- OpenCode：`https://opencode.ai/oauth/opencode/client.json`。

Broker / Authorization Server 在目标客户端兼容时声明 `client_id_metadata_document_supported=true`，并保留 DCR registration endpoint 作为兼容回退。不得在 AirBridge 写入的 MCP Host 配置中设置自定义 `oauth.client_id`、`client_secret` 或 `redirect_uri`，让目标客户端遵循官方 CIMD / DCR 发现流程。

CIMD 安全策略：
- 只比较完整、规范化后的两个精确 HTTPS URL；不接受任意 metadata URL、通配域名、用户输入 URL、URL 中附带 query / fragment 或非标准端口。
- 优先对两个已知官方 Client ID 及其固定 metadata 关键信息 / redirect URI 进行预登记，不发起任意 URL 网络抓取。确因实现需要获取 metadata 时，只允许这两个精确目标，禁止跨域重定向，并对 TLS、DNS 解析结果、响应大小、超时、内容类型和缓存做限制。
- Antigravity IDE 2.6.0+ 可使用 CIMD；旧版或未采用 CIMD 的受支持版本必须验证 DCR 回退。Antigravity 官方 CIMD redirect URI 为 `https://antigravity.google/oauth-callback`，应与该客户端身份一起精确校验。
- OpenCode 只有在 AS 声明支持 CIMD、公有客户端且未设置自定义 `redirect_uri` 时才按官方机制优先 CIMD；loopback callback 应遵守 OpenCode 元数据与 RFC 8252 约束。自定义 redirect URI 会使其回退 DCR。
- DCR 作为兼容回退，不代表新增 Generic / Manual MCP Client 支持。DCR 提交的名称、URL、图标和产品声明均视为未经验证的客户端输入；DCR 注册成功不构成客户端真实性证明。

DCR 与授权隔离：
- 仅接受本地 HTTPS Broker 的受支持 public authorization-code client registration；强制 PKCE S256，校验 grant / response type、token endpoint auth method 和 redirect URI；对注册频率、数量、元数据长度和重复注册进行限制与审计。
- 对 loopback native callback，仅按 RFC 8252 和对应官方 metadata 允许的 host / scheme / path / dynamic port 规则处理；不得接受任意域名、任意 scheme 或开放重定向。
- CIMD / DCR 仅创建 Client Registration，不建立 Grant，不自动授予 Agent / Scope。新 DCR Client 必须在 GUI Consent 中明确展示未经验证的客户端声明。
- 每个 Grant 都必须经用户明确同意，并绑定 `oauth_client_id + agent_instance_id + resource/audience + scopes`。相同 Client ID 请求不同 Agent / Resource 时必须分别 Consent；白名单 CIMD Client ID 也不得跳过授权。
- 认证请求继续验证 PKCE S256、OAuth state、redirect URI 和 RFC 8707 resource / audience；注册身份与 Agent 身份不得混为一谈。
